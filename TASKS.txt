[ x ] BUG 1 — Wrong field name in SolveHub.js
    File: frontend/src/components/SolveHub.js, line 22

    WHAT: Change `solve.plus2` to `solve.plus_two`.

    WHY THIS MATTERS:
    JavaScript doesn't throw an error when you access a property that doesn't
    exist on an object — it just silently returns `undefined`. So `solve.plus2`
    evaluates to undefined, which is falsy, meaning the +2 penalty is NEVER
    added to the time in SolveHub's stats. The solve list (SolveLog.js) uses
    the correct name `plus_two` and works fine, but SolveHub's Best, Average,
    and AO5 numbers are all slightly wrong whenever a +2 is involved.

    LESSON: This is called a "silent failure" — one of the most dangerous kinds
    of bugs because nothing crashes, you just get wrong data. Always verify that
    the field names you use in the frontend exactly match what the API returns.
    A good habit: console.log a response object once and inspect its keys before
    writing code that reads from it.


[ ] BUG 2 — Reset session doesn't delete solves from the database
    File: frontend/src/components/SolveSession.js, lines 80-85

    WHAT: The `resetTimer` function currently only does this:
        setSolveCount(0);
        setSolves([]);
    It needs to also loop through the solves and call `api.deleteSolve()` for
    each one before clearing local state. Or add a backend endpoint like
    DELETE /api/solves?puzzle_type=333 that deletes them all at once.

    WHY THIS MATTERS:
    React state and your database are two completely separate things. Clearing
    state only affects what the user sees RIGHT NOW in the browser. The moment
    they refresh the page, `useEffect` fetches solves from Supabase again and
    all the "deleted" solves come back. This is a very common mistake when
    learning React — assuming that what you see on screen reflects what's in
    the database.

    LESSON: Any time you remove something from UI state, ask yourself: "Does
    this also need to be removed from the server?" If yes, you need an API call.
    The UI should be a reflection of the database, not the other way around.


[ x ] BUG 3 — API URL is hardcoded, ignoring the environment variable
    File: frontend/src/services/api.js, line 4

    WHAT: Change:
        const API_URL = 'http://localhost:5000/api';
    to:
        const API_URL = process.env.REACT_APP_API_URL || 'http://localhost:5000/api';

    WHY THIS MATTERS:
    The frontend/.env file already has REACT_APP_API_URL set. Create React App
    automatically injects variables prefixed with REACT_APP_ into the bundle
    via process.env. But because the code hardcodes the URL, the env var is
    completely ignored. If you ever deploy this (different server address, HTTPS,
    etc.) you'd have to edit source code instead of just changing a config value.

    LESSON: Hardcoded URLs, passwords, or hostnames in source code are called
    "magic strings" — they're a maintenance and security problem. Environment
    variables exist so that your code works in any environment (local, staging,
    production) without code changes. The `|| 'http://localhost:5000/api'` part
    is a fallback in case the env var isn't set, which is good defensive coding.

[ x ] DEBUG 1 — 25+ print() statements in the backend routes
    File: backend/app/routes/solves.py

    WHAT: Delete ALL the print() statements. Every single one. The "=== Auth
    Decorator Start ===" blocks, "Token extracted", "Successfully authenticated",
    all of them.

    WHY THIS MATTERS:
    print() to stdout is fine for debugging but terrible in a running server.
    It clutters logs, can expose sensitive data (user IDs, tokens), and slows
    down request handling. In a real production environment, you'd use Python's
    `logging` module instead, which lets you control log levels (DEBUG, INFO,
    WARNING, ERROR) and turn them on/off without changing code. For this project,
    just removing the prints is the right call.

    LESSON: The difference between debugging and logging: debugging prints are
    temporary, written to understand what's happening right now. Logging is
    intentional, structured output designed to be read in production. Never
    commit debugging prints — use your git staging area (`git add -p`) to
    review every line before committing.


[ x ] DEBUG 2 — console.log prints the auth token on every API call
    File: frontend/src/services/api.js, line 17

    WHAT: Delete this line:
        console.log('Auth headers:', headers)

    WHY THIS MATTERS:
    This logs `Authorization: Bearer eyJ...` to the browser console on every
    single API request. The Bearer token is essentially a temporary password.
    Anyone who opens DevTools on a shared computer, or if you screen-share

[ x ] COMPLEXITY 1 — Every Flask route is registered twice
    File: backend/app/routes/solves.py, lines 41-55 and throughout

    WHAT: Each route has two decorators like this:
        @solves.route('/solves/', methods=['GET'])
        @solves.route('/solves', methods=['GET'])
    Replace all of these with a single decorator. To handle both with and
    without trailing slash automatically, change the Blueprint creation to:
        solves = Blueprint('solves', __name__, strict_slashes=False)

    WHY THIS MATTERS:
    `strict_slashes=False` tells Flask to treat /solves and /solves/ as the
    same route automatically for every route on that Blueprint. Doing it
    manually with two decorators per route is 2x the lines and 2x the chance
    of making a mistake on one of them.

    LESSON: When you find yourself copy-pasting a pattern on EVERY instance of
    something, look for a way to set it once at a higher level. Frameworks like
    Flask almost always have a configuration option for common patterns.

[ x ] COMPLEXITY 4 — Scramble event ID mapping is an identity function
    File: frontend/src/components/Scramble.js, lines 25-35

    WHAT: This entire block:
        const eventId =
          type === '222' ? '222' :
          type === '333' ? '333' :
          type === '444' ? '444' :
          ... (10 lines)
          '333';
    Can be replaced with just:
        const eventId = type;

    WHY THIS MATTERS:
    Every branch of this ternary chain returns the same value it checks. It's
    mapping '333' to '333', '444' to '444', etc. The cubing.js event IDs
    happen to be the exact same strings as your puzzle type values. The only
    "logic" here is the final fallback to '333' if nothing matches, but since
    your puzzle type selector only offers valid event IDs, that can't happen.

    LESSON: When you see a long if/else or ternary chain, ask: "Could this be
    a lookup table (object/map) instead? Or is it even needed?" A 10-way
    identity mapping is a sign the abstraction was built for a problem that
    doesn't exist.


[ x ] COMPLEXITY 5 — Scramble text is read from the DOM instead of React state
    File: frontend/src/components/SolveSession.js, line 43

    WHAT: This line:
        scramble: document.querySelector('.scramble-text')?.textContent || ''
    is grabbing the scramble by querying the DOM directly. Instead, lift the
    scramble state up: add a `scramble` state to SolveSession, pass a
    `onScrambleGenerated` callback prop to the Scramble component, and have
    Scramble call it when it generates a new scramble. Then use that state value
    when creating a solve.

    WHY THIS MATTERS:
    This is one of the most fundamental React anti-patterns: bypassing React's
    data model to read from the DOM directly. React is built around the idea
    that the UI is a function of state — if you want data, you get it from
    state, not by poking at DOM nodes. The DOM query is fragile (it breaks if
    you rename the CSS class), implicit (the connection between SolveSession and
    Scramble is invisible), and bypasses React's rendering lifecycle entirely.

    LESSON: In React, data flows DOWN via props, and events flow UP via
    callbacks. If a child component has data the parent needs, the parent should
    own that state and pass a callback to the child. Never reach into the DOM
    to get data that should be in state.


[ x ] COMPLEXITY 6 — React.StrictMode is commented out
    File: frontend/src/index.js, lines 9-11

    WHAT: Either uncomment StrictMode:
        <React.StrictMode>
          <App />
        </React.StrictMode>
    or delete the commented lines entirely. Don't leave dead comment code.

    WHY THIS MATTERS:
    StrictMode is a development tool that deliberately runs effects and renders

    if you might want something back, delete it confidently knowing git has it.
    Prefer `git stash` or branches over commented-out blocks.
