Input Validation — Defense at the System Boundary

backend/app/validators.py · Security · Small scope

The Problem

The original POST /api/solves blindly took whatever JSON arrived and inserted it straight into the database. Any authenticated user could send:

{ "puzzle_type": "DROP TABLE solves", "time": -999, "dnf": "maybe", "scramble": "A".repeat(100000) }

This won't cause SQL injection (Supabase uses parameterized queries), but it corrupts the user's own data, can break client-side stat computation, and wastes database storage.

The Principle: Validate at System Boundaries

A system boundary is any point where data crosses from an untrusted source into your controlled system — HTTP request bodies, file uploads, message queue payloads, webhook bodies. Internal function calls between your own code don't need defensive validation — you trust your own code. But the HTTP layer is a boundary: you can't trust what arrives there, even if the request is authenticated.

Why authenticated doesn't mean trusted: Authentication answers "who are you?" — not "is your payload valid?" A logged-in user can still send malformed data accidentally (a client bug) or deliberately (API abuse).

What Was Built

validators.py exports two pure functions — no framework, no dependencies, just Python:

def validate_create_solve(data): errors = {} puzzle_type = data.get('puzzle_type') if puzzle_type not in VALID_PUZZLE_TYPES: # allowlist, not blocklist errors['puzzle_type'] = "Must be one of: 222, 333, 444..." time = data.get('time') if isinstance(time, bool) or not isinstance(time, (int, float)): errors['time'] = "Must be a number" elif time <= 0 or time > 3600: # no 1-hour solves errors['time'] = "Must be between 0 and 3600 seconds" if len(data.get('scramble', '')) > 500: errors['scramble'] = "Must be 500 characters or fewer" return errors if errors else None # None means valid

The route calls it before touching the database and returns a structured 422 Unprocessable Entity with field-level errors — the same pattern used by APIs like Stripe and GitHub:

{ "error": "Validation failed", "fields": { "time": "Must be between 0 and 3600 seconds", "puzzle_type": "Must be one of: 222, 333, 444..." } }

The PATCH route uses a second function validate_update_solve and then strips the payload to only the allowed fields before passing it to Supabase — so even if a client sends user_id or time in a PATCH, they're silently ignored:

# Only let dnf and plus_two through — strip everything else allowed = {k: data[k] for k in ('dnf', 'plus_two') if k in data} result = supabase.table('solves').update(allowed)...

Why isinstance(time, bool) check?

In Python, bool is a subclass of int. So isinstance(True, int) returns True. Without the explicit bool check first, True would pass as a valid time value of 1 and False as 0. This is a subtle Python trap.

Resume Talking Point
"I implemented input validation at the HTTP boundary — the only point where data crosses from untrusted external sources into the system. I chose an allowlist approach for puzzle types (explicitly enumerate valid values) over a blocklist, and returned 422 with field-level error messages following the same convention as Stripe's API. The PATCH handler also strips the payload to only the fields that are allowed to change, preventing clients from overwriting immutable fields like user_id or time."
DSA-1

Sliding Window — O(n²) → O(n) Rolling Averages

frontend/src/components/SolveLog.js · Algorithms · Small scope

The Original Bug

The solve log shows an Ao5 next to every solve in the list. The original code computed this with a .map() loop:

// OLD — O(n²) solves.map((_, index) => calculateAverage(solves.slice(index), 5) // slice creates O(n-i) array every time! )

Why is this O(n²)? Array.slice(i) copies every element from position i to the end — that's n-i elements. Summed across the entire loop:

n + (n-1) + (n-2) + ... + 1 = n(n+1)/2 = O(n²) With 500 solves: 500 × 501 / 2 = 125,250 element copies With 1000 solves: 1000 × 1001 / 2 = 500,500 element copies

The Fix: Fixed-Size Window Slicing

Inside calculateAverage, the first thing it does is times.slice(0, 5) — it only ever uses 5 elements. So we were copying potentially thousands of elements to use exactly 5 of them. The fix is trivial:

// NEW — O(n) solves.map((_, index) => calculateAverage(solves.slice(index, index + 5), 5) // always copies exactly 5 )

Now each iteration does O(5) = O(1) work. The entire .map() is O(n).

What is a Sliding Window?

A sliding window is an algorithmic pattern where you maintain a "window" of fixed size that moves across an array one step at a time, reusing computation from the previous position instead of recomputing from scratch.

Solves array (newest first): [8.2, 9.1, 7.5, 10.2, 8.8, 9.3, 7.9, ...] └──────────────────┘ window at index 0 (Ao5 for solve #1) └──────────────────┘ window at index 1 (Ao5 for solve #2) └──────────────────┘ window at index 2 ...

Each window step: slide right by 1. Old element exits, new element enters. For the Ao5 window (size 5), this could be made even more efficient with a running sum and a monotonic deque (to track the min/max that Ao5 drops). The current fix is already a massive improvement — a deque-based approach would go further for very large N but adds significant complexity for a window of size 5.

ApproachTime per render500 solvesNotes
Original (slice tail)O(n²)~125K opsCopies grow with n
Fixed window slice (current)O(n)~2,500 opsAlways copies 5 elements
Sum + monotonic dequeO(n)~500 opsO(1) per step, reuses sum
Resume Talking Point
"I identified an O(n²) bug in the rolling average computation — for each of n solves, it was slicing the entire remaining array to extract just 5 elements. Fixed it to a sliding window that slices exactly the 5-element window at each position, reducing total allocations from O(n²) to O(n). The React useMemo wrapping it means this only runs when the solves array changes, not on every render."
SD-2

Cursor-Based Pagination — Scalable Data Loading

backend/app/routes/solves.py · SolveSession.js · Medium scope

The Problem with Loading Everything

The original GET /api/solves returned every single solve for a user. A dedicated speedcuber can easily accumulate 10,000+ solves. Returning all of them on every page load means:

  • Large JSON payloads over the network
  • Supabase scanning and returning every row
  • React holding the entire dataset in memory
  • The O(n) and O(n²) operations above getting worse over time

Offset Pagination — and Why It's Wrong

The naive solution is offset pagination: LIMIT 50 OFFSET 100. This is how most beginners implement pagination — and it has two serious problems:

Problem 1: Offset re-scans rows SELECT * FROM solves ORDER BY created_at DESC LIMIT 50 OFFSET 500 Postgres must scan and discard 500 rows to reach row 501. At OFFSET 5000, it discards 5000 rows. Gets slower as you page deeper. Problem 2: Offset breaks under concurrent writes Page 1: rows [1, 2, 3, 4, 5] returned ← user reads this ↓ another solve is inserted at position 1 Page 2 (OFFSET 5): rows [5, 6, 7, 8, 9] returned ← row 5 appears TWICE row 1 was pushed down and is now MISSING from page 1

Cursor Pagination — The Right Approach

Instead of "skip N rows", cursor pagination says: "give me everything before this specific row." The cursor is the created_at timestamp of the last row you already have.

# First page — no cursor GET /api/solves?puzzle_type=333&limit=50 # Response includes the next cursor { "solves": [...50 solves...], "next_cursor": "2024-11-15T09:32:11.000Z" ← created_at of last row } # Next page — pass the cursor GET /api/solves?puzzle_type=333&limit=50&cursor=2024-11-15T09:32:11.000Z

The SQL query becomes:

-- Cursor query (uses the B-tree index directly) SELECT * FROM solves WHERE user_id = $1 AND puzzle_type = $2 AND created_at < $cursor -- "everything before the cursor" ORDER BY created_at DESC LIMIT 50;

The composite index in 002_cursor_pagination_index.sql makes this query O(log n):

CREATE INDEX solves_user_puzzle_created_idx ON solves (user_id, puzzle_type, created_at DESC);

Postgres can jump directly to the cursor position in the B-tree and read forward — no rows are scanned and discarded. The query time stays O(log n) whether you're on page 1 or page 100.

B-tree leaf pages (simplified): [user_id=ABC, 333, 2024-12-01] → [user_id=ABC, 333, 2024-11-30] → [user_id=ABC, 333, 2024-11-29] ↑ cursor lands here reads forward from here, no scanning behind

Frontend: "Load More" Pattern

The frontend stores the next_cursor in state. A "Load More" button in SolveLog appends the next page without replacing the existing solves — this is the infinite scroll / progressive loading pattern:

const loadMore = async () => { const { solves: moreData, next_cursor } = await api.getSolves(puzzleType, nextCursor); setSolves(prev => [...prev, ...moreData]); // append, don't replace setNextCursor(next_cursor); // null = no more pages };
Resume Talking Point
"I replaced a full-table load with cursor-based pagination. The key insight is that offset pagination re-scans discarded rows on every request and produces duplicate/missing rows under concurrent inserts — both of which get worse over time. A cursor (the created_at timestamp of the last seen row) lets Postgres use a composite B-tree index to jump directly to the next batch in O(log n), regardless of which page you're on. I added the composite index (user_id, puzzle_type, created_at DESC) to make the WHERE clause sargable."
DSA-2

Binary Search — O(log n) Percentile After Each Solve

frontend/src/components/SolveSession.js · Algorithms · Medium scope

The Feature

After each solve, SolveHub shows: "Faster than 73% of your solves". This requires knowing how the new time ranks among all previous solve times.

The Naive Approach

Re-sort all solves every time. If you have 1,000 solves and add one: sort 1,001 elements → O(n log n) per solve. Over 1,000 solves, that's O(n² log n) total work.

The Right Approach: Maintain a Sorted Copy

Instead of re-sorting, maintain a sorted copy of all valid times alongside the main solves array. When a new solve arrives, insert it into the sorted copy in the right position using binary search — O(log n) to find the position, O(n) to insert (array splice shifts elements). This is the standard sorted-insertion maintenance pattern.

// bisectLeft: returns the leftmost index where val can be inserted // to keep arr sorted. Classic binary search variant. const bisectLeft = (arr, val) => { let lo = 0, hi = arr.length; while (lo < hi) { const mid = (lo + hi) >> 1; // integer divide by 2 (bit shift) if (arr[mid] < val) lo = mid + 1; else hi = mid; } return lo; };
sortedTimes (before new solve): [5.21, 7.83, 9.02, 11.44, 13.10] ↓ New solve: 9.50 bisectLeft([5.21, 7.83, 9.02, 11.44, 13.10], 9.50) → lo=0, hi=5, mid=2 → arr[2]=9.02 < 9.50 → lo=3 → lo=3, hi=5, mid=4 → arr[4]=13.10 > 9.50 → hi=4 → lo=3, hi=4, mid=3 → arr[3]=11.44 > 9.50 → hi=3 → lo=3 == hi=3 → return 3 Position 3: 3 solves are faster, 2 solves are slower. Faster than (2/5) × 100 = 40% of your solves

The Percentile Formula

// pos = number of previous solves FASTER than this one (lower times) // beaten = number of previous solves SLOWER than this one // "Faster than X% of your previous solves" const pos = bisectLeft(prev, time); const beaten = prev.length - pos; const pct = Math.round((beaten / prev.length) * 100);

Why bisectLeft, not bisectRight?

bisectLeft places the new element before any existing equal elements. bisectRight places it after. For computing "how many solves did I beat?", either works for unique times. bisectLeft is the conservative choice — if your time ties with an existing solve, it doesn't inflate your percentile.

OperationRe-sort approachBinary search + sorted copy
Find positionO(n log n)O(log n)
Insert elementO(n log n)O(n) — splice shifts
Total per solveO(n log n)O(log n) find + O(n) insert
After 1,000 solves totalO(n² log n)O(n²) worst — but fast in practice
Why keep a separate sorted array instead of sorting the main solves array? The main solves array is displayed in reverse-chronological order (newest first). Sorting it in place would destroy the display order. Maintaining a separate sorted copy is a classic space-for-time tradeoff — double the memory, but O(log n) lookup instead of O(n log n) sort.
Resume Talking Point
"I maintain a sorted copy of solve times alongside the main reverse-chronological list. On each new solve, I binary search (bisect_left) to find the insertion position in O(log n), compute the percentile from that position, and splice the new time in. This avoids re-sorting on every solve — which would be O(n log n) per solve and O(n² log n) after n solves total."

Personal Best History — Write-Time Materialization (CQRS Lite)

backend/migrations/003_personal_bests.sql · routes/solves.py · SolveHub.js

The Feature

A chart showing how your personal best (PB) for a puzzle improved over time — your fastest solve ever, at each point in history. This answers: "How has my 3x3 PB improved over the past 6 months?"

The Core Design Decision: When Do You Compute PBs?

This is one of the fundamental tradeoffs in system design: compute on read, or compute on write?

Option A — Compute on READ (every request) GET /personal-bests → SELECT MIN(time) FROM solves WHERE user_id=X AND puzzle_type=333 → ... and how do we get the PB history? We'd have to scan ALL solves in order, track the running minimum, emit a row each time it drops. → O(n) scan, every request. At 10,000 solves, that's 10,000 rows scanned. Option B — Compute on WRITE (current implementation) POST /solves (new solve arrives) → Insert solve ✓ → Check: is this time < current PB recorded in personal_bests? → If yes: insert one row into personal_bests GET /personal-bests → SELECT * FROM personal_bests WHERE user_id=X AND puzzle_type=333 → Returns only the PB rows — O(1) index scan regardless of solve count
This is the CQRS principle in miniature. CQRS = Command Query Responsibility Segregation. Commands (writes) pay a small extra cost to maintain derived state. Queries (reads) pay almost nothing. The personal_bests table is a write-time materialized view — a denormalized, derived table that's kept up-to-date on every write.

The Schema

CREATE TABLE personal_bests ( id uuid DEFAULT gen_random_uuid() PRIMARY KEY, user_id uuid REFERENCES auth.users NOT NULL, puzzle_type text NOT NULL, time numeric NOT NULL, -- the PB time itself achieved_at timestamptz NOT NULL, -- when this PB was set solve_id uuid REFERENCES solves(id) ON DELETE SET NULL -- which solve it came from );

Row Level Security ensures users can only read their own PBs — same pattern as the solves table.

The Write-Time Logic

def _maybe_record_pb(supabase, user_id, puzzle_type, new_time, ...): # Query the current PB from the personal_bests table pb_result = supabase.table('personal_bests') .select('time') .eq('user_id', user_id) .eq('puzzle_type', puzzle_type) .order('time') ← sort ascending, take best .limit(1) .execute() current_pb = pb_result.data[0]['time'] if pb_result.data else None if current_pb is None or new_time < current_pb: ← new PB! supabase.table('personal_bests').insert({...}).execute()

The function is called after the main solve insert and is wrapped in a try/except that swallows errors. The PB tracking is best-effort — if it fails (Supabase hiccup, network blip), the solve is still saved successfully. The user doesn't see an error. This is a deliberate decision: PB history is secondary data; the solve itself is primary.

The Tradeoffs You Should Know

ConcernImpactDecision
Race conditionsTwo concurrent solves could both think they're a PBAcceptable — speedcubers time one solve at a time
StorageA new row per PB event (rare writes)Tiny — most users have <100 PBs ever
PB after deleteIf you delete your PB solve, personal_bests still has itsolve_id SET NULL on delete; chart is historical, not live
Resume Talking Point
"I faced a choice: compute PB history on every GET by scanning all solves in order, or materialize it at write time. I chose write-time materialization — the personal_bests table is updated on every non-DNF POST /solves. This keeps GET /personal-bests to an O(1) indexed query regardless of how many solves exist, at the cost of one extra query per solve insertion. This is the CQRS pattern: commands pay a small extra cost so queries are cheap. The PB tracking is also best-effort — if it fails, the solve insert still succeeds."

Circular Buffer — O(1) Fixed-Window Tracking

frontend/src/hooks/useCircularBuffer.js · Data Structures · Small scope

What is a Circular Buffer?

A circular buffer (also called a ring buffer) is a fixed-capacity array that reuses its own storage. When it's full, the next write overwrites the oldest element. Two pointers — head (next write position) and size — are all you need to track state.

Buffer of capacity 5, after pushing [A, B, C, D, E]: index: [ 0 1 2 3 4 ] items: [ A B C D E ] ↑ head=0 (wraps back to start) Push F: items: [ F B C D E ] ← A is overwritten ↑ head=1 toArray() reads from head → head+size, wrapping: [B, C, D, E, F] ✓

Why O(1) push matters

OperationArray.push + sliceCircular Buffer
Add item to endO(1)O(1)
Evict oldest (keep last N)O(n) — splice or sliceO(1) — overwrite slot, move head
Read all itemsO(n)O(n)
Memory allocationNew array on every evictionFixed array, reused forever

For a window of 12, the difference in absolute terms is tiny. But the circular buffer teaches the concept used in real systems everywhere: OS kernel network receive buffers, audio playback buffers, log rotation, the Linux kernel's kfifo.

The Implementation

const useCircularBuffer = (capacity) => { // useRef, not useState — push() must not trigger re-renders const state = useRef({ items: new Array(capacity).fill(null), head: 0, // next write slot (= oldest item when full) size: 0, }); const push = useCallback((item) => { const s = state.current; s.items[s.head] = item; // overwrite oldest slot s.head = (s.head + 1) % capacity; // advance, wrap around if (s.size < capacity) s.size += 1; // track fill level }, [capacity]); const toArray = useCallback(() => { const { items, head, size } = state.current; const start = size < capacity ? 0 : head; // oldest item position return Array.from({ length: size }, (_, i) => items[(start + i) % capacity]); // walk oldest → newest }, []); return { push, toArray, reset }; };

Key React Decision: useRef not useState

The buffer state lives in a useRef, not useState. This is intentional: push() should not cause a re-render. The buffer is a write-only side structure — components read it through toArray() which is called in a useMemo that depends on solves. When solves changes (from a new solve or delete), the memo recalculates, which calls toArray(), which reads the current buffer state. No spurious re-renders from the buffer itself.

Where it's used: SolveSession maintains a capacity-12 buffer. As new solves arrive via handleSolveComplete, they're pushed to the buffer — O(1). SolveHub receives recentSolves (the last 12, from toArray()) and uses them for the solve-time chart instead of slicing from the full array.
Resume Talking Point
"I implemented a circular buffer as a custom React hook to track the last 12 solves without allocating a new array on each insertion. The key design choice was using useRef instead of useState — push() should not trigger re-renders, since the buffer is a write-only side structure that components consume via toArray() inside a useMemo that's already gated on the solves array changing."

Token Bucket Rate Limiting — API Abuse Prevention

backend/app/extensions.py · routes/solves.py · Security · Small scope

Why Rate Limit?

Without rate limiting, any authenticated user can hammer the API — intentionally or from a client bug running in a loop. A tight loop of POST /solves could insert thousands of rows per minute, inflating storage and compute costs. GET /solves loops could stress the database. Rate limiting gives you a predictable upper bound on API traffic per client.

Three Common Rate Limiting Algorithms

AlgorithmHow it worksBurst behaviorComplexity
Fixed Window Count requests in a fixed time bucket (e.g., this minute). Reset to 0 at minute boundary. Allows 2× burst at window boundary (last second of minute + first second of next) O(1)
Sliding Window Log Store timestamp of every request, count how many are in the past N seconds. Exact — no boundary burst O(requests) storage
Token Bucket (current) Bucket holds up to C tokens, refills at rate R tokens/sec. Each request consumes 1 token. Block if empty. Allows bursts up to capacity C, then enforces rate R O(1) time, O(1) storage

Token Bucket Intuition

Bucket capacity: C = 30 tokens Refill rate: R = 0.5 tokens/sec (30/min) t=0s: bucket=[●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●] 30 tokens full t=0s: 25 requests arrive instantly → bucket=[●●●●●] 5 tokens left → all served t=1s: 1 more request → bucket=[●●●●●+●] refilled 0.5 → served t=2s: 5 requests arrive → bucket=[●] → 1 served, 4 blocked ... Bursts are absorbed (up to C). Sustained rate is capped at R.

The Implementation

# extensions.py — single limiter instance, shared across routes from flask_limiter import Limiter from flask_limiter.util import get_remote_address limiter = Limiter(key_func=get_remote_address, storage_uri="memory://") # __init__.py — plugs into the Flask app factory limiter.init_app(app) # routes/solves.py — per-route limits @solves.route('/solves', methods=['GET']) @require_auth @limiter.limit("60 per minute") ← 1 request/sec sustained def get_solves(): ... @solves.route('/solves', methods=['POST']) @require_auth @limiter.limit("30 per minute") ← tighter: you can't spam solves def create_solve(): ...

When the limit is exceeded, Flask-Limiter automatically returns:

HTTP/1.1 429 Too Many Requests Retry-After: 14 { "error": "30 per 1 minute" }

Flask App Factory Pattern

The limiter is created in extensions.py (without an app reference) and then initialized in create_app() via limiter.init_app(app). This is Flask's Application Factory pattern. It's important here because:

  • Routes import limiter from extensions to use @limiter.limit()
  • The app isn't created yet when routes are imported (circular import risk)
  • init_app defers app binding until the factory runs — safe and testable
Current limitation: The key function is IP address. Behind a load balancer or NAT, multiple users might share an IP and eat each other's quota. Production systems use authenticated user ID as the key — but that requires the rate check to run after auth, which is the order we already have (@require_auth runs before @limiter.limit in the call chain).
Resume Talking Point
"I added rate limiting using the token bucket algorithm — 30 requests/min on POST /solves and 60/min on GET. Token bucket was the right choice over fixed window because fixed window allows a 2× burst at the window boundary (end of one window + start of next). Token bucket smooths this out: it allows short bursts up to capacity C, then enforces the sustained rate. I used Flask-Limiter's Application Factory pattern so the limiter instance is created in extensions.py without an app reference, then wired in via init_app — avoiding circular imports between the factory and the routes."

WCA Inspection Timer — State Machine Design

frontend/src/components/Timer.js · UX · Medium scope

The Feature

WCA regulations give competitors 15 seconds of inspection time before each solve. During inspection you can look at the cube; the solve clock starts only when you touch the timer. If you exceed 15 seconds, a +2 penalty is applied (adds 2 seconds to the result). Exceeding 17 seconds is a DNF.

The Problem with Booleans

The original Timer used two booleans — isRunning and isReady — to track state. Adding inspection requires a third phase. Two booleans already have 4 possible combinations (3 of which are valid, 1 is illegal). A third boolean would give 8 combinations — 6 illegal. This is a classic state explosion: the code becomes a mess of if (!isRunning && !isReady && !isInspecting) guards.

The boolean flag trap: Each boolean added to represent a new phase multiplies the total state space by 2. Most combinations are illegal and must be explicitly prevented. Bugs emerge when you forget to guard one of them.

The Solution: A Phase Enum (Finite State Machine)

Replace the booleans with a single phase string that can only ever hold one of four values. This is a Finite State Machine (FSM) — a well-known pattern for managing UI that has multiple exclusive modes.

State machine: IDLE ──(space down)──> READY ──(space up)──> INSPECTION ──(space down)──> RUNNING ^ │ └──────────────────────────────(space down)─────────────────────────────────────┘ INSPECTION: countdown ticks from 15 → 0 every 100ms RUNNING: solve timer counts up every 10ms Transition RUNNING → IDLE: record inspectionMs elapsed, flag +2 if > 15000ms

Stale Closure Problem — Why phaseRef is Needed

React event handlers registered in useEffect capture the state values at the time the effect runs — a classic JavaScript closure. If phase state changes, the old handler still sees the old phase. The fix: keep a phaseRef that is always mutated synchronously alongside the state update. Event handlers read from phaseRef.current; React renders read from phase state.

// phaseRef drives keyboard logic; phase state drives rendering. const phaseRef = useRef('idle'); const [phase, setPhase] = useState('idle'); const handleKeyDown = (event) => { const p = phaseRef.current; // always fresh — not a stale closure if (p === 'idle') { phaseRef.current = 'ready'; setPhase('ready'); } else if (p === 'inspection') { startRunning(); } else if (p === 'running') { finishSolve(); } };

Inspection Countdown Implementation

const startInspection = useCallback(() => { inspectionStartRef.current = Date.now(); setInspectionCount(15); // Tick every 100ms — no need for 10ms precision on a countdown inspectionIntervalRef.current = setInterval(() => { const elapsed = Date.now() - inspectionStartRef.current; const remaining = Math.max(0, Math.ceil((15000 - elapsed) / 1000)); setInspectionCount(remaining); }, 100); phaseRef.current = 'inspection'; setPhase('inspection'); }, []);

Penalty Rule

Date.now() - inspectionStartRef.current : 0; const inspectionOverran = inspectionElapsed > 15000; phaseRef.current = 'idle'; setPhase('idle'); onSolveComplete(timeRef.current / 1000, inspectionOverran); }, [onSolveComplete]); // SolveSession receives inspectionOverran and sets plus_two on the new solve: const newSolve = { puzzle_type, time, dnf: false, plus_two: inspectionOverran, scramble };

Resume Talking Point
"Adding a third phase (inspection) to a two-boolean timer caused state explosion — two booleans produce 4 combinations, 3 of which are valid, but a third boolean gives 8 with only 4 valid. I replaced the booleans with a phase enum, making the state machine explicit and the transitions impossible to violate. I also separated the phaseRef (always fresh, used in event handlers) from the phase state (used for rendering) to solve the stale closure problem that arises when useEffect registers event listeners that need to read current state."

Two-Heap Running Median — O(log n) Median of a Data Stream

frontend/src/hooks/useMedianTracker.js · Data Structures · Medium scope

The Problem

The average solve time is already shown in SolveHub, but average is skewed by outliers — a single terrible solve drags it up significantly. The median is more robust. A speedcuber's median time is a truer reflection of their "typical" solve.

Why Not Just Sort?

Sorting all times on every new solve is O(n log n). Over n solves total, that's O(n² log n). At 1,000 solves, you're doing roughly 10 million operations per solve just to find the middle element.

The Two-Heap Algorithm

Maintain two heaps that together hold all solve times, split at the median:

lo: max-heap of the lower half (peek = largest of lower half = left of median) hi: min-heap of the upper half (peek = smallest of upper half = right of median) Invariant: lo.size >= hi.size and lo.size - hi.size <= 1 Example with times [5.2, 7.8, 9.0, 11.4, 13.1]: lo (max-heap): [9.0, 7.8, 5.2] ← peek = 9.0 (the middle element) hi (min-heap): [11.4, 13.1] ← peek = 11.4 odd total (5) → median = lo.peek() = 9.0 After adding 10.5: lo: [9.0, 7.8, 5.2] hi: [10.5, 11.4, 13.1] even total (6) → median = (lo.peek() + hi.peek()) / 2 = (9.0 + 10.5) / 2 = 9.75

Push Algorithm

function push(val) { // Route new value to the correct heap if (lo.size === 0 || val <= lo.peek()) { lo.push(val); // belongs in lower half } else { hi.push(val); // belongs in upper half } // Rebalance: keep sizes within 1 of each other if (lo.size < hi.size) lo.push(hi.pop()); // hi too big if (lo.size - hi.size > 1) hi.push(lo.pop()); // lo too big } function getMedian() { if (lo.size === 0) return null; return lo.size > hi.size ? lo.peek() : (lo.peek() + hi.peek()) / 2; }

JS Heap Implementation

JavaScript has no built-in heap. The hook implements a minimal BinaryHeap class parameterised by a compare function — max-heap uses (a, b) => a > b, min-heap uses (a, b) => a < b. Both push and pop are O(log n) via bubble-up/sink-down.

const lo = useRef(new BinaryHeap((a, b) => a > b)); // max-heap const hi = useRef(new BinaryHeap((a, b) => a < b)); // min-heap // Stored in refs — mutations don't trigger re-renders (same pattern as DSA-3)

Why Two Separate Structures for Median vs Percentile?

DSA-2 maintains a sorted array for percentile queries — you need the rank of a given time, which requires knowing how many times are below it. The sorted array gives you that in O(log n) via binary search.

DSA-4 maintains two heaps for the median — you need the middle value, which only requires knowing the top of each half. The heaps give you that in O(1). They're complementary: different query types, different data structures, both maintained in parallel.

Deletion caveat: Heaps don't support efficient arbitrary deletion. When a solve is deleted, the tracker resets and rebuilds from the sortedTimesRef in O(n). This is acceptable — deletions are rare (one at a time, user-initiated). For a production system needing frequent deletions, an order-statistic tree (e.g. a balanced BST with augmented subtree sizes) would handle both median and rank queries with O(log n) delete.

Optimistic Updates with Rollback — Eventual Consistency at the UI Layer

frontend/src/components/SolveSession.js · System Design · Small scope

The Problem with Pessimistic Updates

The original handleSolveUpdate and handleSolveDelete waited for the API response before updating the UI — a pessimistic approach. On a fast connection this is invisible, but on mobile or a slow 3G connection, toggling a DNF feels broken: you tap, nothing happens, the UI freezes for 2–3 seconds, then updates. This is especially jarring in a timer app used between rapid-fire solves.

// BEFORE — pessimistic: wait for server before touching UI const result = await api.updateSolve(id, data); setSolves(prev => prev.map(s => s.id === result.id ? result : s));

Optimistic Updates: The Pattern

An optimistic update assumes the server will agree and updates the UI immediately. If the server returns an error, roll back to the pre-mutation snapshot. This makes the UI feel instantaneous for the common path (success), while remaining correct for the uncommon path (failure).

// AFTER — optimistic: update UI first, roll back on failure const snapshot = solves; // capture before mutation setSolves(prev => prev.map(s => s.id === updated.id ? updated : s)); // immediate try { await api.updateSolve(updated.id, updated); // fire in background } catch { setSolves(snapshot); // rollback on failure }

Three Concepts This Demonstrates

1. Eventual Consistency. After the optimistic update, the local UI state and the server state temporarily diverge — the UI has already applied the change, but the network request is still in flight. If the request succeeds, both sides converge. If it fails, the rollback re-converges them. This is the same eventual consistency model that distributed databases (Cassandra, DynamoDB) use: accept writes locally, propagate later, resolve conflicts.

2. Idempotency. PATCH and DELETE are safe to use optimistically because they're idempotent — applying the same operation twice has the same effect as once. If you toggle DNF on a solve that's already DNF (e.g., due to a race condition or retry), the result is the same: DNF. This is why REST chose these verbs for update/delete, and why optimistic updates are safer with PATCH/DELETE than with POST.

3. Snapshot before mutation. The snapshot must be captured before the mutation, not after. If you captured it after setSolves(), the snapshot would already contain the optimistic change — your "rollback" would not actually restore anything. This ordering is easy to get wrong.

// Delete: optimistic remove + sorted-times + median rollback const handleSolveDelete = async (solveToDelete) => { const snapshot = solves; // ← BEFORE, not after const sortedSnapshot = sortedTimesRef.current; setSolves(prev => prev.filter(s => s.id !== solveToDelete.id)); // immediate // ... update sorted times and rebuild median tracker ... try { await api.deleteSolve(solveToDelete.id); } catch (err) { setSolves(snapshot); // rollback UI sortedTimesRef.current = sortedSnapshot; // rollback ref medianTracker.reset(); // rollback heaps sortedSnapshot.forEach(v => medianTracker.push(v)); } };
