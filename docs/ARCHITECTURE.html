The 30-Second Pitch

What to say when someone asks "what did you build?"

Ao5 (also called Decipher) is a full-stack speedcubing timer web app. Users sign in (or use guest mode), solve any of 15 WCA puzzles with a spacebar or touch interface, and their times are saved to a database. The app computes rolling statistics (Ao5, Ao12, session mean, running median, percentile rank), tracks personal bests, charts performance over time, and includes case-by-case algorithm trainers for OLL, PLL, F2L, and CMLL.

Sentence version: "A real-time puzzle timer with persistent solve history, rolling average stats, personal-best tracking, distribution charts, OLL/PLL trainers, share-link snapshots, and a guest mode that migrates seamlessly on first sign-in. Built with React 18 + TypeScript, Flask 3, and Supabase, with JWT auth (local JWKS verification with a Supabase fallback) and row-level security enforced at the database layer."

What makes it non-trivial

It is not just a CRUD app. The interesting parts are: a high-precision timer with phase state machine and direct-DOM writes during the running phase to avoid 60Hz re-renders; client-side scramble generation for 15 WCA puzzle types via cubing.js; a stateless Flask backend that acts as an authenticated proxy with two-path JWT verification (local JWKS fast path, Supabase fallback); row-level security so the database itself enforces data ownership; cursor-based pagination with `(created_at, id)` tiebreaker; write-time materialization of personal-best history via an atomic Postgres RPC; a per-user counter table to enforce a 100,000-solve lifetime cap atomically; HMAC-signed share-link tokens with 30-day TTL; a virtualized solve log; TanStack Query for cross-page cache consistency; structured JSON logging with request-scoped IDs; and several DSA improvements (sliding window Ao5, binary-search percentile, two-heap running median, circular buffer for the recent-solves chart).

Why three layers?

The browser cannot talk to the database directly for data operations. The anon key ships to every visitor, and client-side code can be tampered with. The Flask backend acts as a trusted intermediary: it validates identity (JWT), enforces business rules (validation, rate limits, lifetime cap), and forwards the request to Supabase using the user's own token so that Supabase's row-level security still applies at the database layer. Even a bug in Flask cannot expose another user's data; PostgreSQL itself rejects the query.

Note that auth itself is handled directly between the browser and Supabase (no Flask involved). The Supabase JS client manages the login flow and stores the resulting JWT. That JWT is then attached to every Flask API call as a Bearer token. Flask is not in the login flow at all. This is the correct pattern: auth servers should talk directly to clients, not be proxied.

The AuthClient seam

The frontend never imports from @supabase/supabase-js directly outside of one file (services/auth.ts). Everything else goes through the AuthClient interface in services/authClient.ts:

interface AuthClient { getAccessToken(): Promise<string | null>; signInWithPassword(email: string, password: string): Promise<{ error?: string }>; signUp(email: string, password: string): Promise<{ error?: string }>; signOut(): Promise<{ error?: string }>; resetPasswordForEmail(email: string, redirectTo: string): Promise<{ error?: string }>; updatePassword(password: string): Promise<{ error?: string }>; onSignIn(callback: () => void): () => void; }

This three-method seam means swapping Supabase for a different auth provider (Auth0, Clerk, hand-rolled) touches one file. Without the seam, every supabase.auth.* call site would need refactoring.

Technology Choices and Tradeoffs

The "why" behind every tool in the stack

Vite + React 18 vs. Next.js vs. Vue

OptionKey traitWhy chosen / not chosen
Vite + React 18 ✓ Pure client-side SPA, fast dev server, ESM-native This app is entirely behind a login wall (or a public share token). There is nothing to prerender or SEO-index. SSR (Next.js's main benefit) provides zero value here. Vite gives instant HMR and small production bundles via Rollup. Migrated from Create React App in early development; CRA is unmaintained.
Next.js SSR, file-based routing, API routes, edge functions Adds real complexity (SSR hydration, server components, route handlers) for no benefit when every interactive page requires authentication. The shared share-link page is one route and renders fine on the client.
Vue / Svelte Smaller bundles, simpler reactivity Smaller ecosystems for libraries like Recharts, @nivo/calendar, and cubing.js. React is the dominant choice in industry; choosing it maximizes the resume signal and keeps third-party options open.

TypeScript strict + noUncheckedIndexedAccess

The frontend was migrated to TypeScript with strict: true and noUncheckedIndexedAccess: true. The latter makes arr[i] typed as T | undefined, forcing every indexed access to either narrow the type or assert. Caught a wave of latent bugs during the F.1 audit pass. Combined with `isPuzzleType`-style predicates, the URL query parameter for the puzzle picker can never leak an invalid value into the type system.

TanStack Query for solves cache

OptionKey traitWhy chosen / not chosen
TanStack Query ✓ Server-state cache with key-based invalidation Solves are fetched on the timer page (paginated) and on the Stats page (full history). Without a shared cache, creating a solve on the timer page would not appear on Stats until manual refetch. With TanStack Query, both pages share ['solves', puzzleType, ...] keys; mutations call invalidateSolveCaches and the other page refetches on next view. Also handles request cancellation (AbortSignal threaded through axios).
SWR Lighter, simpler API Roughly equivalent feature set; TanStack Query is more capable on mutations and was the audit's recommendation (H.3).
Hand-rolled cache via Context Zero deps Re-implementing query key invalidation, request cancellation, refetch-on-focus, and stale-while-revalidate is a meaningful project. Adopting a small, well-maintained library was the better tradeoff.

Flask vs. FastAPI vs. Django vs. Node

OptionKey traitWhy chosen / not chosen
Flask 3 ✓ Micro-framework, minimal opinions, mature The backend is a thin authenticated proxy. It does not own the database, does not need an ORM, does not need admin panels or form handling. Flask is exactly as powerful as needed and no more. The Blueprint pattern + service/repository layering gives clean structure. Flask 3 also has good CSP, security-header, and error-handler ergonomics.
FastAPI Async, automatic OpenAPI, Pydantic validation Async provides no real benefit when every Supabase call is awaited and the bottleneck is a single network round-trip. Pydantic adds a C extension compile step that bit us on the dev machine (Python 3.14, Xcode license issue). Hand-rolled validators.py is small, fast, and has zero compile dependencies.
Django Batteries-included: ORM, admin, migrations, forms Massive overkill. Django shines when you own a database through its ORM. Here, Supabase manages the database. You would be carrying all of Django's weight while using almost none of it.
Node / Express Same language as frontend No technical reason to avoid it, but Flask is the stronger resume choice for a Python-fluent engineer. The frontend/backend language split is fine; they communicate over HTTP, not in-process.

Supabase vs. Firebase vs. raw PostgreSQL

OptionKey traitWhy chosen / not chosen
Supabase ✓ Managed PostgreSQL + auth + PostgREST + RLS Real relational database (joins, constraints, complex queries, ACID transactions, triggers, RPCs), managed auth with JWT issuance, and row-level security enforced at the database engine level. Free tier is generous. Right tool for structured, relational data.
Firebase (Firestore) NoSQL document store Solve data is inherently relational. Each solve belongs to a user, has a puzzle type, a time, flags. NoSQL would require application-level access control instead of database-level RLS. Queries like "min time per puzzle type" become awkward. Firebase security rules are harder to reason about than SQL policies.
Raw PostgreSQL (self-hosted) Full control You manage connection pooling, backups, auth tokens, migrations, and a PostgREST equivalent yourself. Supabase wraps all of this. The tradeoff is vendor lock-in. Supabase-specific features (RLS policies, auth.uid()) would need rewriting to migrate.

PyJWT for local JWT verification

Originally every authenticated request did a network round-trip to Supabase to verify the JWT. Switched to PyJWT with cached JWKS as a fast path; Supabase fallback only fires on local-verification failure (legacy HS256 tokens, JWKS unreachable, key rotation lag). Documented in docs/jwt-verification.md. Eliminated the per-request network call for the common path.

cubing.js for scrambles

Scrambles are generated client-side using cubing.js for the timer and a small in-house generator for the trainer routes (which need case-by-case scrambles with prepended setup moves). The alternative would be a backend endpoint.

Why client-side? Scramble generation is CPU-bound, especially for big cubes (5x5, 6x6, 7x7). Running it on the server means every solve would require a network round-trip before the user can start timing. Client-side is instant and works offline. The tradeoff is bundle size; cubing.js is not small. For a dedicated speedcubing app where users expect instant scrambles, client-side wins decisively. Lazy-loading the trainer route keeps the initial bundle lean.

Auth Flow Deep Dive

JWT, JWKS fast path, AuthClient seam, and the require_auth decorator

What is a JWT?

A JSON Web Token is a self-contained credential. It has three Base64-encoded parts separated by dots: header.payload.signature. The payload contains claims like sub (the user ID), email, aud (audience), iss (issuer), and exp (expiration). The signature is produced by the auth server using a private key (asymmetric ES256/RS256 in our case).

eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiJ1c2VyLTEyMyIsImF1ZCI6ImF1dGhlbnRpY2F0ZWQiLi4ufQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c │ │ │ header (alg) payload (claims) signature { sub: "user-123", aud: "authenticated", iss: "https://<project>.supabase.co/auth/v1", exp: 1735000000 } ← unix timestamp

Anyone can read the payload (Base64, not encrypted). Only the auth server can produce a valid signature. With asymmetric algorithms, anyone with the public key can verify, but only the holder of the private key can sign. JWKS (JSON Web Key Set) is the standard endpoint that publishes the public keys.

The full auth flow

1
User submits email + password to Auth.tsx
The form calls supabaseAuthClient.signInWithPassword(email, password). The AuthClient seam calls supabase.auth.signInWithPassword internally; this hits Supabase's auth endpoint directly. Flask is not in the login flow.
2
Supabase returns a JWT + refresh token
The JWT has a short expiry (~1 hour). The refresh token lets Supabase issue a new JWT silently when the current one expires. Both are stored in localStorage by the Supabase JS client. (Token storage strategy is a known long-term concern; the recorded decision is at docs/decisions/2026-04-26-token-storage.md.)
3
AuthContext fires SIGNED_IN; routes update
AuthProvider subscribes to onAuthStateChange. When SIGNED_IN arrives, it fires the AuthClient's onSignIn callback, which kicks off any guest-to-auth migration if guest solves exist in localStorage.
4
Every API call attaches the JWT as a Bearer token
services/api.ts calls supabaseAuthClient.getAccessToken() before every request. Axios includes it as Authorization: Bearer <token>. The api wrapper also parses the standardized error envelope on non-2xx responses.
5
Flask require_auth: fast path via local JWKS
verify_token_local(token) uses PyJWT to decode the token against Supabase's published JWKS. The JWKS client is a process-wide singleton initialized lazily under a threading lock, with a 5-minute cache lifespan. On success, returns the user_id (sub claim). On token-shape failures (expired, bad signature, wrong issuer, wrong audience), logs at DEBUG and returns None.
6
Flask require_auth: slow path on fast-path failure
If verify_token_local returns None, fall back to supabase.auth.get_user(jwt=token) (a network round-trip). Logs event=auth_slow_path at INFO so operators can grep fallback rate. Sustained spikes mean JWKS unreachability or recent key rotation.
7
Flask sets g.user_id and g.supabase, runs the route
flask.g is request-scoped. g.user_id is set from the JWT subject; g.supabase is a Supabase client created with postgrest.auth(token), so all queries from this request run as that user and RLS applies.

JWT vs. session cookies — why JWT here

JWT (current)Session cookies
Server stateNone — stateless. Flask stores nothing.Requires a session store (Redis, DB table). Every request does a lookup.
ScalabilityAny Flask instance can validate any JWT — just needs the JWKS public keys (cached).All instances must share the same session store, or use sticky sessions.
RevocationA JWT is valid until its exp claim. A logged-out user's token technically still works until expiry (~1hr).Delete the session row — revoked instantly.
Cross-originWorks naturally across different domains (frontend on Vercel, backend on Render).Cookies require SameSite=None; Secure for cross-origin, plus CORS credentials config.

Statelessness wins for this app. Supabase handles the short expiry plus refresh-token rotation, which mitigates the revocation concern. The backend never needs to store state.

The require_auth decorator

def require_auth(f): @wraps(f) def decorated(*args, **kwargs): auth_header = request.headers.get('Authorization', '') if not auth_header.startswith(BEARER_PREFIX): return error_response(AUTH_MISSING_TOKEN, "No authorization token provided", 401) token = auth_header.removeprefix(BEARER_PREFIX).strip() if not token: return error_response(AUTH_MISSING_TOKEN, "No authorization token provided", 401) # Fast path: local JWKS user_id = verify_token_local(token) if user_id is None: # Slow path; logged so operators can track fallback rate logger.info("auth_slow_path event=auth_slow_path") try: supabase = get_supabase_client(token) user = supabase.auth.get_user(jwt=token) except Exception: current_app.logger.exception("Supabase auth lookup failed") return error_response(AUTH_UNAVAILABLE, "Auth service unavailable", 503) if not user or not getattr(user, 'user', None): return error_response(AUTH_INVALID_TOKEN, "Invalid authentication token", 401) user_id = user.user.id g.supabase = supabase else: g.supabase = get_supabase_client(token) g.user_id = user_id return f(*args, **kwargs) return decorated

The decorator pattern (vs. global middleware) is deliberate. /api/health and /api/ready are public; you can see at a glance which routes are protected. Public routes that take a share token (GET /api/v1/solves/share/<token>) skip require_auth and rely on the share-link signature verification instead.

Talking Point
"Authentication is handled entirely between the browser and Supabase. Flask is never in the login flow. The frontend gets a JWT and attaches it as a Bearer token on every API call. Flask validates the signature using a two-path scheme: a fast local JWKS verification via PyJWT for the common case (millisecond, zero network calls), with a Supabase auth.get_user fallback for legacy tokens or JWKS outages. The slow path emits a structured log event so we can monitor fallback rate. Once verified, Flask creates a Supabase client scoped to the user's token so PostgreSQL row-level security still applies at the database. Two independent layers of access control."

Request Lifecycle — Spacebar to Database

What actually happens when you stop the timer
1
User releases spacebar
The keyup handler in useTimerMachine fires inside Timer.tsx. The timer reads its time directly from timeRef.current (mutated by the RAF loop). RAF is cancelled, the phase ref transitions to 'idle', and onSolveComplete(time, inspectionOverran) fires.
2
useSolveSession.handleSolveComplete
Builds a solve payload from time, current puzzle type, the current scramble (managed by scrambleQueue), and inspection-overran flag (sets plus_two: true if the user exceeded 15s).
3
Optimistic local update
A temporary solve with a placeholder id is prepended to local state immediately. UI feels instant. Sorted-times array gets a binary-search insert; running median tracker pushes the new value; circular buffer pushes too.
4
api.createSolve — axios POST to Flask
services/api.ts fetches the current access token via supabaseAuthClient.getAccessToken() and POSTs to /api/v1/solves with Authorization: Bearer <token>. The axios interceptor parses the standardized error envelope on failure.
5
Flask: before_request hooks fire
_attach_request_id sets g.request_id = uuid4().hex. _legacy_api_deprecation tags the request if it landed on the unversioned /api mount. Then route dispatch.
6
require_auth: validate JWT (fast → slow)
Local JWKS verification first. On failure, Supabase fallback with auth_slow_path log. Sets g.user_id and g.supabase.
7
Rate limit and validation
flask-limiter checks g.user_id bucket (30/min for create_solve). validate_create_solve(data) runs allowlist-based checks, returns 422 with field errors on failure.
8
SolvesService.create_solve
Reads the user_stats row to check the 100,000 lifetime cap (atomic counter, not a count(*) query). Inserts the solve via SolvesRepository. The insert triggers update_user_solve_count, which atomically increments user_stats.solve_count.
9
Atomic PB write via Postgres RPC
If the solve is not DNF, calls record_pb_if_better(user_id, puzzle_type, solve_id, time) via .rpc(). The RPC compares against existing PBs and inserts a new PB row in a single transaction. No race conditions; previously this was two round-trips with TOCTOU.
10
after_request: structured access log
_access_log emits one JSON line via app.access logger: {"timestamp": "...", "level": "INFO", "message": "POST /api/v1/solves 201", "request_id": "...", "user_id": "..."}. Security headers and the response are returned.
11
Frontend: server response replaces optimistic record
The temp solve is swapped for the server-assigned id, created_at, and any other DB-generated fields. invalidateSolveCaches(qc, puzzleType) tells TanStack Query that the Stats page's full-list query is stale, so the next visit to /stats refetches.
12
scrambleQueue advances; new scramble appears
Decoupled from the API call. The queue keeps the next scramble ready in the background so there is no pause between solves.

Frontend Architecture

Routing, state ownership, TanStack Query, and the component tree

Routing shell

The top-level App.tsx is a routing shell. It mounts an ErrorBoundary at the root, then a Routes tree with all non-timer routes wrapped in React.lazy so their bundles do not load until needed. The home route (timer) is intentionally eager so the most common path is fast.

main.tsx └── QueryClientProvider └── AuthProvider └── SettingsProvider + ScramblePreviewSettingsProvider └── ThemedToaster (sonner) └── App.tsx — ErrorBoundary + Routes │ ├── / → SolveSession (timer; eager) ├── /stats → Stats (lazy) ├── /trainers → Trainers (lazy) ├── /s/:token → SharedSolve (lazy) └── /login → Auth (lazy)

The SolveSession orchestrator

The timer page's logic lives in useSolveSession, which composes several smaller hooks: useSortedSolveStats (maintains the sorted-times array, percentile, and median tracker), useReplayState (consumes the location state when navigating from a solve detail's "use this scramble" button), and a TanStack Query subscription for the active page of solves. The previous monolithic 290-line hook was split during the E.9 refactor.

TanStack Query for solves

Solves are fetched through useAllSolvesQuery(puzzleType, isGuest) from queries/solves.ts. The query key is ['solves', puzzleType, 'full', isGuest]. After every mutation (create, update, delete), useSolveSession calls invalidateSolveCaches(qc, puzzleType), which invalidates everything keyed under ['solves', puzzleType]. The Stats page subscribes to the same key, so it sees fresh data on next mount without manual coordination.

Cancellation: The query function receives an AbortSignal that is threaded into api.getSolves(puzzleType, cursor, signal). Switching puzzles mid-fetch cancels in-flight requests. Visible in DevTools Network as canceled requests when throttled to slow 3G.

Why useSolveSession is the orchestrator

Single source of truth. React's data model is unidirectional. SolveSession owns the active page of solves; all of its child components receive what they need via props. The TanStack Query cache is the underlying source of truth for the full history; useSolveSession manages the local, mutation-aware view of it.

The scramble queue

Scramble generation is async and CPU-bound (especially for big cubes). The scrambleQueue in lib/scrambleQueue.ts keeps the next scramble pre-generated so there is no visible pause between solves. The current scramble is rendered as text in Scramble.tsx and (when enabled in settings) as a 3D preview in ScramblePreview.tsx using cubing.js's TwistyPlayer.

Memoization, useCallback, useMemo

The codebase makes liberal use of useCallback on event handlers and useMemo on derived values. The audit's C cluster identified specific hot paths where stale-identity callbacks were causing re-render storms; those are all resolved. The Timer's running phase writes directly to a DOM ref via textContent instead of calling setState 60 times per second.

The lazy-loaded routes

Stats, Trainers, SharedSolve, and Auth are wrapped in React.lazy. The Suspense fallback is a small div with aria-busy="true". This keeps Recharts, @nivo/calendar, and the trainer's case data out of the timer route bundle. Bundle analyzer confirms separate chunks.

Talking Point
"The frontend uses React 18 + TypeScript strict + noUncheckedIndexedAccess. Routing is a thin shell with lazy-loaded routes and a top-level error boundary. Server state lives in TanStack Query so creating a solve on the timer page invalidates the Stats query and the user sees fresh data on next navigation. UI state lives in component-local hooks. The biggest hook, useSolveSession, was decomposed into focused sub-hooks during the audit — useSortedSolveStats handles the sorted-times array and median tracker, useReplayState handles navigation-based replay, the original hook is now a thin orchestrator."

Backend Architecture

Service + repository layers, error envelope, structured logging

The authenticated proxy pattern

Flask's job is narrow and well-defined: validate the JWT, run validation and rate limiting, then forward the request to Supabase using the user's own token. It does not own a database connection pool, does not manage schema migrations, and does not store session state. It is a stateless processing layer.

Why not call Supabase directly from the frontend? For reads with RLS, you technically could. But for writes you need server-side validation; the frontend can be tampered with. Rate limiting needs to happen server-side. The lifetime cap needs an atomic check that the frontend cannot bypass. The backend gives you a single, auditable point where every request is inspected before it reaches the database.

Service + repository layering

The audit's E.11 refactor split the previous monolithic routes/solves.py into three layers:

# routes/solves.py — thin HTTP adapter @solves.route('/solves', methods=['POST']) @require_auth @limiter.limit("30 per minute") def create_solve(): data = request.get_json() errors = validate_create_solve(data) if errors: return error_response(VALIDATION_FAILED, "Validation failed", 422, fields=errors) try: solve = service.create_solve(g.user_id, data) except SolveLimitReached: return error_response(SOLVE_LIMIT_REACHED, "Solve limit reached", 429) return jsonify(solve), 201 # services/solves_service.py — business logic class SolvesService: def create_solve(self, user_id, data): count = self.repo.get_solve_count(user_id) if count >= SOLVE_LIFETIME_CAP: raise SolveLimitReached() solve = self.repo.insert_solve(user_id, data) if not solve['dnf']: self.pb_repo.record_pb_if_better(...) # RPC call, atomic return solve # repositories/solves_repo.py — Supabase access class SolvesRepository: def insert_solve(self, user_id, data): result = self.supabase.table('solves').insert({...}).execute() return result.data[0]

Routes do HTTP. Services do business logic. Repositories own Supabase access. Tests can mock at any layer.

Standardized error envelope

Every 4xx/5xx response goes through error_response(code, message, status, fields=None) from app/errors.py:

{ "error": { "code": "SOLVE_LIMIT_REACHED", // stable upper-snake-case "message": "Solve limit reached", // human-readable "fields": { "time": "Must be > 0" } // optional, present on 422 } }

Frontend switches on code for branching; falls back to message for unknown codes. Codes are documented in backend/app/errors.py. Even framework-emitted errors (rate limit 429, missing route 404, generic 500) go through the same envelope via app-level @app.errorhandler registrations.

The /api/v1 prefix and the legacy alias

The blueprint is registered twice: once at /api/v1 (canonical) and once at /api (transitional). The legacy mount is required because saved share-link URLs are in the wild. After the sunset date, the legacy mount and its hooks can be deleted.

The dangerous_admin module

The service-role Supabase key bypasses RLS. Any code path using it is a potential RLS-bypass vector and needs careful review. The H.8 refactor moved get_supabase_service_client from db.py into backend/app/dangerous_admin.py:

"""Service-role Supabase client — BYPASSES RLS. Only call this with explicit, audited authorization. Currently used only by the share-link read route, which has its own signature verification. """ def get_supabase_service_client(): ...

The import path is loud at the call site: from ..dangerous_admin import get_supabase_service_client. Code review can grep for that import string. Currently only the share-read route imports it.

Rate limiter

extensions.py exports a single Limiter instance that keys on g.user_id when authenticated, falling back to get_remote_address() for anonymous routes. Auth runs before the limit check via decorator ordering. Storage is in-memory by default; LIMITER_STORAGE_URI env var swaps to Redis for multi-process deployments without code changes.

Per-request Supabase client

A new Supabase client is created per request inside require_auth and stored on g.supabase. This is intentional: each request runs as that specific user so RLS sees the correct auth.uid(). Sharing a global client would mean all requests run as the service role, bypassing RLS. The per-request cost is negligible; create_client just constructs an HTTP client with the right headers.

Database Design

Schema, RLS, indexes, triggers, RPCs

The solves table

CREATE TABLE solves ( id uuid DEFAULT gen_random_uuid() PRIMARY KEY, user_id uuid REFERENCES auth.users ON DELETE CASCADE NOT NULL, puzzle_type text NOT NULL, -- '333', '444', 'pyram', etc. time numeric NOT NULL, -- seconds, e.g. 12.47 dnf boolean DEFAULT false, plus_two boolean DEFAULT false, scramble text DEFAULT '', created_at timestamptz DEFAULT now() NOT NULL, deleted_at timestamptz, -- soft delete; NULL means active metadata jsonb DEFAULT '{}' -- forward-compat for enrichment );

UUID primary key over sequential integer: unguessable, can be generated client-side, safe to expose in URLs (share links use them). 16 bytes vs 4 is negligible at this table size.

numeric for time over float: exact decimal arithmetic in PostgreSQL. float would have floating-point precision errors (12.47 might become 12.469999...). For times displayed to the user, exact values matter.

ON DELETE CASCADE on user_id: deleting a Supabase auth user automatically cleans up their solves. Same for personal_bests. Audit D.3 added this.

deleted_at for soft delete: A.6 + B.6. Hard delete would orphan share-link tokens and break PB references. Soft delete preserves history; reads filter WHERE deleted_at IS NULL via the partial index.

metadata jsonb default '{}': H.12 forward-compat column for future enrichment fields (device, app version, comp tags). No code reads it today.

The personal_bests table

CREATE TABLE personal_bests ( id uuid DEFAULT gen_random_uuid() PRIMARY KEY, user_id uuid REFERENCES auth.users ON DELETE CASCADE NOT NULL, puzzle_type text NOT NULL, time numeric NOT NULL, achieved_at timestamptz NOT NULL, solve_id uuid REFERENCES solves(id) ON DELETE SET NULL );

Write-time materialized view of the running minimum solve time per puzzle, per user. Updated by the atomic record_pb_if_better RPC (migration 010) at solve insert time. The Stats page reads this directly for the PB progression chart in O(1) instead of scanning all solves.

The user_stats counter table

CREATE TABLE user_stats ( user_id uuid PRIMARY KEY REFERENCES auth.users ON DELETE CASCADE, solve_count integer NOT NULL DEFAULT 0 ); CREATE FUNCTION update_user_solve_count() RETURNS trigger AS $$ BEGIN IF (TG_OP = 'INSERT') THEN INSERT INTO user_stats (user_id, solve_count) VALUES (NEW.user_id, 1) ON CONFLICT (user_id) DO UPDATE SET solve_count = user_stats.solve_count + 1; ELSIF (TG_OP = 'UPDATE' AND OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL) THEN UPDATE user_stats SET solve_count = solve_count - 1 WHERE user_id = NEW.user_id; END IF; RETURN NULL; END; $$ LANGUAGE plpgsql; CREATE TRIGGER solves_solve_count_trigger AFTER INSERT OR UPDATE ON solves FOR EACH ROW EXECUTE FUNCTION update_user_solve_count();

The 100,000-solve lifetime cap (audit A.2 + D.4) was originally enforced by a count(*) query before every insert. That had two problems: (1) slow at scale, (2) a TOCTOU race meant two concurrent inserts could both think they were below the cap. The counter table fixes both: read is a single index lookup; the trigger is atomic inside the insert transaction.

Row Level Security

ALTER TABLE solves ENABLE ROW LEVEL SECURITY; -- Per-operation policies, all gating on auth.uid() = user_id CREATE POLICY "Users can view own solves" ON solves FOR SELECT USING (auth.uid() = user_id); CREATE POLICY "Users can insert own solves" ON solves FOR INSERT WITH CHECK (auth.uid() = user_id); CREATE POLICY "Users can update own solves" ON solves FOR UPDATE USING (auth.uid() = user_id); CREATE POLICY "Users can delete own solves" ON solves FOR DELETE USING (auth.uid() = user_id); -- Same shape on personal_bests, plus the audit's A.9 fix: CREATE POLICY "Users can delete own personal bests" ON personal_bests FOR DELETE USING (auth.uid() = user_id); CREATE POLICY "Users can update own personal bests" ON personal_bests FOR UPDATE USING (auth.uid() = user_id);

RLS is enforced by the PostgreSQL engine itself, not by application code. Even if there is a bug in Flask that accidentally passes the wrong user_id, the database rejects it. Even if someone bypasses Flask and calls Supabase's PostgREST API directly with a valid JWT, they still cannot read another user's solves.

Defense in depth: Access control is enforced at three independent layers — (1) the Supabase JS client only works when logged in, (2) Flask's require_auth validates the JWT and scopes queries to the user, (3) PostgreSQL RLS physically prevents cross-user data access at the row level. A vulnerability in any single layer does not compromise the data.

Indexes

-- Cursor pagination over active solves (D.1: includes deleted_at predicate) CREATE INDEX solves_user_puzzle_created_active_idx ON solves (user_id, puzzle_type, created_at DESC) WHERE deleted_at IS NULL; -- PB-min lookup by time (D.2) CREATE INDEX personal_bests_user_puzzle_min_time_idx ON personal_bests (user_id, puzzle_type, time ASC);

The partial index on solves makes the WHERE clause sargable without a recheck row in the query plan. Composite column order matters: most selective filter (user_id) first.

Atomic PB write via RPC

Audit D.8 replaced the read-then-insert PB pattern with a single atomic RPC:

CREATE FUNCTION record_pb_if_better( p_user_id uuid, p_puzzle_type text, p_solve_id uuid, p_time numeric ) RETURNS void AS $$ BEGIN INSERT INTO personal_bests (user_id, puzzle_type, time, achieved_at, solve_id) SELECT p_user_id, p_puzzle_type, p_time, now(), p_solve_id WHERE NOT EXISTS ( SELECT 1 FROM personal_bests WHERE user_id = p_user_id AND puzzle_type = p_puzzle_type AND time <= p_time ); END; $$ LANGUAGE plpgsql SECURITY INVOKER;

One round-trip, atomic. Concurrent inserts cannot race to insert duplicate PB rows for ties.

Cursor pagination with tiebreaker

# Cursor encodes (created_at, id) so identical microsecond timestamps # do not drop a row across pages. cursor_str = b64encode(f"{created_at}|{id}".encode()) # Decoder accepts both shapes for one release window (D.9) def _decode_solve_cursor(s): decoded = b64decode(s).decode() if "|" in decoded: ts, solve_id = decoded.split("|", 1) return ts, solve_id return decoded, None # legacy: timestamp only

Tiebreaker means duplicate timestamps (rare but possible under bulk inserts) cannot drop a row across pages. The query becomes WHERE created_at < X OR (created_at = X AND id < Y).

Talking Point
"I chose Supabase over Firebase because the data is fundamentally relational. PostgreSQL's row-level security means the database itself enforces data ownership. The schema includes a per-user counter table maintained by trigger to enforce a 100,000-solve cap atomically — a count(*) check would have a TOCTOU race. Personal-best history is a write-time materialized view updated by an atomic Postgres function so concurrent solves cannot race. Soft delete via deleted_at preserves history and keeps share links valid. Cursor pagination uses (created_at, id) as the tiebreaker so identical-timestamp inserts cannot drop a row across pages."

CSP currently ships as Content-Security-Policy-Report-Only (phase 1). Browsers report violations to DevTools but do not block. After a one-to-two-week burn-in with no violations in production, the header name flips to Content-Security-Policy (phase 2) and violations actively block.

Per-user rate limiter

Audit B.10 changed the limiter key from IP to authenticated user (with IP fallback for anonymous routes). Behind a corporate NAT, IP-based limiting punishes innocent users; for an attacker, IP rotation evades it. User-keyed limiting is fairer and tighter.

Why Bearer tokens prevent CSRF: CSRF works by tricking a victim's browser into making a request to your API while the victim is logged in. The browser automatically includes cookies. Bearer tokens (in localStorage, attached by JavaScript) are never automatically included by the browser on cross-origin requests. An attacker's site cannot access localStorage from another origin. CSRF is structurally impossible with Bearer token auth.

Share Links

Stateless HMAC tokens with embedded TTL

The feature

From the SolveDetailModal, an authenticated user can mint a read-only public link to a single solve: https://<host>/s/<token>. Anyone with the link can view the solve (time, scramble, date) without signing in. The link expires after 30 days.

Token format

b64url(solve_id).b64url(iat).b64url(exp).b64url(mac) │ │ │ │ │ │ │ └── HMAC-SHA256(SHARE_SECRET, "id:iat:exp")[:16] │ │ └── unix timestamp 8 bytes big-endian │ └── unix timestamp 8 bytes big-endian └── solve UUID

Stateless: no database lookup needed to verify. The verifier recomputes the MAC and checks expiry. If either fails, 404.

Why this design

OptionApproachTradeoff
Stateless HMAC (current) ✓ Sign with SHARE_SECRET; embed iat + exp in payload No DB writes per share, no DB reads per verify, naturally expiring. Cap blast radius via TTL.
DB-backed share_links table Random opaque token; row stores solve_id, expiry, optional revoked_at Needed if per-link revocation matters. Adds a write per share, a read per verify, and a migration. Documented in audit A.7 option 2 as a future option.
Plaintext id only The URL contains the solve UUID directly Anyone with a UUID guesses no one else's, but tampering is trivial — change a character and try someone else's solve. No expiry. Was the original (broken) implementation.

SHARE_SECRET rotation

Rotation invalidates every outstanding link the instant the new secret takes effect. The runbook at docs/share-secret-rotation.md documents the hard-cutover procedure today and a recommended future dual-secret rolling-window pattern (~30 lines of Python) if frequent rotation becomes necessary.

SHARE_SECRET length floor: create_app refuses to boot if SHARE_SECRET is shorter than 32 characters. Generate with python -c "import secrets; print(secrets.token_urlsafe(48))".

Guest Mode

localStorage-backed solves with one-shot migration on sign-in

Why guest mode

The friction of sign-up before trying the timer is real. Guest mode lets a visitor solve immediately; if they sign up later, their solves migrate in one batched request to POST /api/v1/solves/batch.

How it works

1
No auth required to use the timer
AuthContext.isGuest is true when there is no session. useSolveSession branches on this: in guest mode it reads from and writes to services/guestStorage, which uses localStorage with a per-puzzle key prefix.
2
Guest solves accumulate in localStorage
Each puzzle has its own key. Stats, SolveLog, and the chart all read from the same store. Lifetime cap and PB tracking do not apply in guest mode (intentional simplification).
3
Sign in or sign up
The AuthClient's onSignIn callback fires. AuthContext checks for guest solves; if any exist, sorts them chronologically (B.12: out-of-order migration would corrupt PB materialization) and POSTs them in one batch.
4
Backend batch insert + PB recompute
POST /api/v1/solves/batch validates each solve (caps at 1,000), inserts in a single transaction, then calls recompute_pbs_for_user RPC to rebuild PB rows from scratch in chronological order. Separate rate-limit bucket (5/min).
5
Migration toast; localStorage cleared on success
Sonner toast confirms the count migrated. Failed solves (rare) are reported with their error codes; the user can retry. Local solves are cleared after a successful migration.

Detailed feature matrix in docs/guest-mode.md.

Timer Architecture

Phase state machine, RAF + textContent, useTimerMachine extraction

The phase state machine

The timer has four exclusive phases: idle, ready, inspection, running. Booleans (isRunning, isReady) would explode combinations and admit illegal states. A phase enum makes the state machine explicit.

IDLE ──(space down)──> READY ──(space up)──> INSPECTION ──(space down)──> RUNNING ^ │ └──────────────────────────────(space down)────────────────────────────────────┘ INSPECTION: countdown ticks 15 → 0; +2 if > 15s, DNF if > 17s (at user discretion) RUNNING: RAF loop writes elapsed milliseconds directly to the DOM Transition RUNNING → IDLE: read elapsed from timeRef.current, fire onSolveComplete

useTimerMachine hook (E.10 extraction)

The timer's logic was extracted from Timer.tsx into hooks/useTimerMachine.ts. The component became a 60-line presentational shell. The hook owns:

  • phaseRef + phase state — see stale-closure section below
  • timeRef — RAF-mutated, current elapsed ms
  • RAF handle and inspection interval
  • Keyboard and touch event handlers
  • Inspection countdown via tickInspection(elapsed) pure helper (also extracted, fully unit-testable)

The stale-closure problem and the ref fix

React event handlers registered in useEffect capture state values at the time the effect runs. If phase state changes, the old handler still sees the old value. The fix: phaseRef is mutated synchronously alongside the state update; event handlers read from the ref, React renders read from the state.

const phaseRef = useRef<Phase>('idle'); const [phase, setPhase] = useState<Phase>('idle'); const setPhaseSync = (next: Phase) => { phaseRef.current = next; // for event handlers (always fresh) setPhase(next); // for rendering }; const handleKeyDown = (event: KeyboardEvent) => { const p = phaseRef.current; // not stale if (p === 'idle') setPhaseSync('ready'); else if (p === 'inspection') startRunning(); else if (p === 'running') finishSolve(); };

RAF + textContent: zero re-renders during running

The naïve approach calls setTime 60 times per second to update the displayed elapsed milliseconds. That triggers a React commit on every tick. The C.1 audit pass replaced this with direct DOM writes:

const timerNodeRef = useRef<HTMLDivElement>(null); const tick = () => { const elapsed = performance.now() - startRef.current; timeRef.current = elapsed; if (timerNodeRef.current) { timerNodeRef.current.textContent = formatTime(elapsed / 1000); } rafIdRef.current = requestAnimationFrame(tick); };

React commits zero times during the running phase. Only phase transitions cause re-renders. Confirmed via React DevTools Profiler.

Inspection countdown

Inspection ticks every 250ms but only updates state when the displayed integer second changes (audit C.2). This produces ~4 renders per visible second change instead of 10/s.

Penalty rule

If inspectionMs > 15000, the resulting solve is flagged plus_two: true. The display flashes red at > 12s and yellow at > 8s.

Talking Point
"The timer is a four-phase state machine implemented with a phase enum. Two booleans would have produced 4 combinations, three booleans 8 — most of which are illegal. The phase enum makes the state space explicit and impossible to violate. To capture the exact elapsed milliseconds at the moment of stop without React closure staleness, I keep a phaseRef synchronized with the phase state — event handlers read the ref, React reads the state. During the running phase, RAF writes directly to a DOM ref's textContent so React commits zero times for 5-10 seconds of solving. Profiler confirms a flat flame graph between phase transitions."

State Management Strategy

TanStack Query for server state, hooks for UI state, no Redux

Server state vs. UI state

The codebase distinguishes two kinds of state:

  • Server state (solves, personal bests): owned by Supabase, cached locally by TanStack Query. Mutations invalidate keys; consumers refetch on next view.
  • UI state (timer phase, modal open/close, settings panel): owned by React component-local hooks. No global store needed because the tree is shallow and state stays close to its consumer.

Why TanStack Query over Redux/Zustand

Server state has fundamentally different needs from UI state: cache invalidation, deduplication, request cancellation, refetch-on-focus, stale-while-revalidate. Redux and Zustand are general-purpose stores that do not solve these problems out of the box; you would re-implement them. TanStack Query is purpose-built for this.

Observability

Structured logging, /api/ready, slow-path counter, error boundary

Structured JSON logging

Hand-rolled JsonFormatter wired via stdlib logging.config.dictConfig from create_app. Every log line is a single JSON object on stdout:

{ "timestamp": "2026-04-29T20:05:03.332867+00:00", "level": "INFO", "logger": "app.access", "message": "GET /api/v1/solves 200", "request_id": "a114d46e6bd8426781140344dee43f5f", "user_id": "7c3e..." }

request_id is set by a before_request hook (uuid hex). user_id is folded in when present on flask.g (set by require_auth). Operators can pipe stdout through jq for ad-hoc analysis.

Slow-path counter

require_auth emits auth_slow_path event=auth_slow_path at INFO whenever it falls back from local JWKS to supabase.auth.get_user. Operators aggregate this to track fallback rate. Healthy steady state is under 1% of authenticated requests; sustained spikes above 5% mean JWKS unreachability or recent key rotation.

Readiness probe at /api/ready

@app.route('/api/ready') def readiness_check(): checks = {} overall_ok = True try: client = db_module.get_supabase_client() client.table('solves').select('id').limit(1).execute() checks['supabase'] = 'ok' except Exception: checks['supabase'] = 'fail'; overall_ok = False checks['jwks'] = jwks_cache_state() # 'fresh' or 'cold' return jsonify({"status": "ready" if overall_ok else "not_ready", "checks": checks}), \ (200 if overall_ok else 503)

Distinct from /api/health, which is a liveness probe (always 200 if the process is up). The readiness check actually pings Supabase and reports the JWKS cache state — useful for Kubernetes-style readiness gating.

Top-level Error Boundary

Frontend wraps <Routes> in ErrorBoundary (audit H.5). A render-time throw in any route now produces a fallback UI with a "Reload" button and a sonner toast, instead of a blank screen. Lazy-route load failures are caught too. Vendor-pick error reporting (Sentry / PostHog / Highlight / GlitchTip) is deferred (H.6).

Full Interview Script

How to walk someone through this project in 4-6 minutes

Opening (30 seconds)

"Ao5 is a speedcubing timer app — fully full-stack: a React 18 + TypeScript frontend on Vite, a Flask 3 backend acting as an authenticated proxy, and Supabase as the hosted PostgreSQL database. Users sign in (or use guest mode), solve puzzles with the spacebar, and their times are saved with rolling stats like Ao5 and Ao12, a personal-best progression chart, a running median, OLL/PLL trainers, and shareable read-only solve links."

Architecture (60 seconds)

"The architecture is three layers. The React frontend handles all UI and talks to Flask over HTTP. Flask validates the JWT on every request — fast path is local JWKS verification via PyJWT, slow path falls back to Supabase auth.get_user with an INFO log so we can watch fallback rate. Then it runs validation, rate limiting, and forwards to Supabase using the user's own token so row-level security applies at the database layer. The frontend talks to the Supabase JS client through an AuthClient seam so the rest of the app does not couple directly to Supabase. Auth itself is direct browser-to-Supabase; Flask is not in the login flow."

Interesting engineering decisions (90 seconds)

"A few things I'm particularly happy about. First, the timer uses a phase state machine with both a ref and state — the ref drives event handlers without stale closures, the state drives rendering. During the running phase RAF writes directly to a DOM ref's textContent so React commits zero times during a 5-10 second solve. Second, I replaced an O(n²) rolling Ao5 with a sliding window. Third, I replaced count(*) cap checks with an atomic per-user counter table maintained by trigger — the original had a TOCTOU race that could let a user exceed the lifetime cap. Fourth, personal-best history uses write-time materialization via an atomic Postgres function, so concurrent solves cannot race. Fifth, share links are stateless HMAC tokens with embedded TTL — no per-share DB write, no per-verify DB read, naturally expiring after 30 days. Sixth, TanStack Query gives cross-page cache consistency: creating a solve on the timer page invalidates the Stats page query so it sees the new solve on next view without manual coordination."

Technology choices (45 seconds)

"I chose Vite + React 18 over Next.js because every interactive page requires authentication; SSR provides zero benefit when there is nothing to prerender. Flask over Django because this backend is a thin proxy, not a full application framework. Supabase over Firebase because the data is fundamentally relational and PostgreSQL's row-level security gives database-engine-level access control. Hand-rolled validators over Pydantic to avoid a C compile step. PyJWT with cached JWKS for the fast path so the common case never needs a network round-trip. TanStack Query for server state because it solves cache invalidation and request cancellation out of the box."

What you would do differently (30 seconds)

"Three things on the deferred list. One, wire an error reporting vendor — the error boundary is in place but the dashboard is not. Two, swap the rate limiter storage from in-memory to Redis when the deployment moves multi-process. Three, migrate from Bearer-token-in-localStorage to PKCE plus an httpOnly cookie via @supabase/ssr — the current scheme has full account takeover as the XSS impact, which the CSP mitigates but does not eliminate. The decision is recorded; implementation is XL and architectural so it lives separately."
