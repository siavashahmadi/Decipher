The 30-Second Pitch

What to say when someone asks "what did you build?"

Ao5 is a full-stack speedcubing timer web app. Users log in, solve WCA puzzles with a spacebar or touch interface, and their times are saved to a database. The app computes rolling statistics — Ao5, Ao12, session mean, personal bests — and charts performance over time.

Sentence version: "A real-time puzzle timer with persistent solve history, rolling average stats, personal best tracking, and a progression chart — built with React, Flask, and Supabase, with JWT-based authentication and row-level security enforced at the database layer."

What makes it non-trivial

It's not just a CRUD app. The interesting parts are: a high-precision timer that avoids React's stale closure problem with a ref; client-side scramble generation for 15 WCA puzzle types via cubing.js; a stateless Flask backend that acts as an authenticated proxy, validating JWTs on every request; row-level security so the database itself enforces data ownership; cursor-based pagination replacing a naive full-table load; write-time materialization of personal best history; and several DSA improvements (sliding window, binary search, circular buffer).

Why three layers?

The frontend can't talk to the database directly for data operations — the anon key would be exposed and client-side code can be tampered with. The Flask backend acts as a trusted intermediary: it validates identity (JWT), enforces business rules (validation, rate limits), and then forwards the request to Supabase using the user's own token so that Supabase's row-level security still applies.

Note that auth itself is handled directly between the browser and Supabase (no Flask involved). The Supabase JS client manages the login flow and stores the resulting JWT. That JWT is then attached to every Flask API call. This is the correct pattern — auth servers should talk directly to clients, not be proxied.

Monorepo structure

Deployment independence: The frontend and backend deploy independently. Frontend goes to a static CDN (zero cost, globally fast). Backend goes to a small server instance. They communicate only over HTTP. You could swap the backend for a completely different language/framework and the frontend wouldn't need to change, as long as the API contract stays the same.

Technology Choices & Tradeoffs

The "why" behind every tool — this is what interviewers actually want to hear

React (Create React App) vs. Next.js vs. Vue

OptionKey traitWhy chosen / not chosen
React CRA ✓ Pure client-side SPA This app is entirely behind a login wall — there's nothing to prerender or SEO-index. SSR (Next.js's main benefit) provides zero value here. CRA gives you a simple, well-understood React environment with no framework opinions on routing or data fetching.
Next.js SSR, file-based routing, edge functions Adds real complexity (SSR hydration, API routes, build configuration) for no benefit when every page requires authentication. "Don't pay costs you don't collect benefits from."
Vue / Svelte Smaller bundle, simpler reactivity Smaller ecosystem for libraries like recharts. React is the dominant choice in industry — choosing it maximizes the resume signal.

Flask vs. FastAPI vs. Django vs. Node/Express

OptionKey traitWhy chosen / not chosen
Flask ✓ Micro-framework, minimal opinions The backend is a thin authenticated proxy — it doesn't own the database, doesn't need an ORM, doesn't need admin panels or form handling. Flask is exactly as powerful as needed and no more. The Blueprint pattern gives clean route organization without framework overhead.
FastAPI Async, automatic OpenAPI docs, Pydantic validation Async provides no real benefit when the bottleneck is Supabase network round-trips (which you'd still await). Pydantic adds a C extension compile step — problematic on this machine (Python 3.14, Xcode license issue). We built our own thin validation layer instead.
Django Batteries-included: ORM, admin, migrations, forms Massive overkill. Django shines when you own a database through its ORM. Here, Supabase manages the database. You'd be carrying all of Django's weight while using almost none of it.
Node/Express Same language as frontend No technical reason to avoid it, but Flask is the stronger resume choice for a Python-fluent engineer. The frontend/backend language split is fine — they communicate over HTTP, not in-process.

Supabase vs. Firebase vs. Raw PostgreSQL

OptionKey traitWhy chosen / not chosen
Supabase ✓ Managed PostgreSQL + auth + PostgREST + RLS You get a real relational database (joins, constraints, complex queries, ACID transactions), managed auth with JWT issuance, and row-level security enforced at the database engine level. The free tier is generous. It's the right tool for structured, relational data.
Firebase (Firestore) NoSQL document store Solve data is inherently relational — each solve belongs to a user, has a puzzle type, a time, flags. NoSQL would require application-level access control instead of database-level RLS. Queries like "min time per puzzle type" become awkward. Firebase's security rules are harder to reason about than SQL policies.
Raw PostgreSQL (self-hosted) Full control You'd manage connection pooling, backups, auth tokens, migrations, and a PostgREST equivalent yourself. Supabase wraps all of this for free. The tradeoff is vendor lock-in — Supabase-specific features (RLS policies, auth.uid()) would need rewriting to migrate.

cubing.js for Scrambles

Scrambles are generated client-side using cubing.js — a well-maintained open-source library that generates WCA-legal random-state scrambles for all 15 official puzzles. The alternative would be a backend endpoint that calls the library server-side.

Why client-side? Scramble generation is CPU-bound (especially for big cubes like 5x5 and 6x6). Running it on the server means every solve would require a server round-trip before the user can start timing. Client-side is instant and works offline. The tradeoff is bundle size — cubing.js is not small. For a dedicated speedcubing app where users expect instant scrambles, client-side wins decisively.

Auth Flow Deep Dive

JWT, Supabase auth, and the require_auth decorator

What is a JWT?

A JSON Web Token (JWT) is a self-contained credential. It has three Base64-encoded parts separated by dots: header.payload.signature. The payload contains claims like sub (the user ID), email, and exp (expiration). The signature is produced by the auth server using a secret key.

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyLTEyMyIsImVtYWlsIjoiLi4uIn0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c │ │ │ header (alg) payload (claims) signature { sub: "user-123", email: "...", exp: 1735000000 } ← unix timestamp

The key property: anyone can read the payload (it's just Base64 encoded, not encrypted). But only the auth server can produce a valid signature. A verifier checks the signature using the public key — if it matches, the claims are trusted. If someone tampers with the payload, the signature breaks.

The Full Auth Flow

1
User submits email + password in Auth.js
Supabase JS client calls supabase.auth.signInWithPassword() — this hits Supabase's auth endpoint directly, not our Flask backend. Flask is not involved in login at all.
2
Supabase returns a JWT + refresh token
The JWT has a short expiry (~1 hour). The refresh token lets Supabase issue a new JWT silently when the current one expires. Both are stored in localStorage by the Supabase JS client automatically.
3
React state updates — App.js shows the timer
App.js listens to supabase.auth.onAuthStateChange(). When the session arrives, it sets session state, which renders <SolveSession> instead of <Auth>.
4
Every API call attaches the JWT as a Bearer token
api.js calls supabase.auth.getSession() before every request and extracts the access_token. Axios includes it as Authorization: Bearer <token>.
5
Flask's require_auth decorator validates the JWT
The decorator calls supabase.auth.get_user(jwt=token). This asks Supabase to verify the signature and return the user object. If valid, request.user_id is set. If not, 401.
6
Flask forwards the user's token to Supabase for DB queries
The Supabase client is created with client.postgrest.auth(access_token) — this tells PostgREST to run queries as that user. Supabase's RLS policies then use auth.uid() to scope every query to that user's rows.

JWT vs. Session Cookies — Why JWT Here?

JWT (current)Session cookies
Server stateNone — stateless. Flask doesn't store anything.Requires a session store (Redis, DB table) — every request does a lookup.
ScalabilityAny Flask instance can validate any JWT — just needs the Supabase key.All instances must share the same session store, or use sticky sessions.
RevocationYou can't invalidate a JWT before it expires (~1hr). A logged-out user's token technically still works until expiry.Delete the session row — revoked instantly.
Cross-originWorks naturally across different domains (frontend on Vercel, backend on Railway).Cookies require SameSite=None; Secure for cross-origin, plus CORS credentials config.

For this app, statelessness wins. Supabase handles the short expiry + refresh token rotation, which mitigates the revocation concern. The backend never needs to store state.

The require_auth decorator

def require_auth(f): @wraps(f) # preserves function name for Flask routing def decorated(*args, **kwargs): token = request.headers.get('Authorization').split(' ')[1] # Ask Supabase to verify the JWT signature + expiry user = supabase.auth.get_user(jwt=token) # Attach user_id and authenticated client to the request context request.user_id = user.user.id request.supabase = get_supabase_client(token) # ← user-scoped client return f(*args, **kwargs) return decorated

The decorator pattern (vs. middleware) is a deliberate choice. Flask middleware (@app.before_request) runs on every request — but /api/health should be public. The decorator is explicit: you can see at a glance which routes are protected. The tradeoff is you could forget to add it to a new route — but this is mitigated by code review and the fact that Supabase's RLS is a second line of defense anyway.

Talking Point
"Authentication is handled by Supabase entirely on the frontend — Flask is not in the login flow at all. The frontend gets a JWT from Supabase and attaches it as a Bearer token on every API call. Flask validates the signature by calling back to Supabase, extracts the user ID, then creates a Supabase client scoped to that user's token so that PostgreSQL row-level security policies still apply at the database layer. This gives us two independent layers of access control."

Request Lifecycle — Spacebar to Database

What actually happens when you stop the timer
1
User releases spacebar
The keyup event listener in Timer.js fires. stopTimer() reads timeRef.current (not time state — see Timer section), converts milliseconds to seconds, and calls onSolveComplete(time).
2
SolveSession.handleSolveComplete fires
Builds a newSolve object from the time, current puzzle type, and the current scramble string (which was captured when cubing.js generated it and stored in SolveSession state).
3
api.createSolve() — Axios POST to Flask
api.js fetches the current Supabase session, extracts the JWT, and makes POST /api/solves with Authorization: Bearer <token>.
4
Flask: require_auth → validate_create_solve → RLS insert
Auth check, then schema validation (422 if bad), then supabase.table('solves').insert(data).execute(). The user-scoped token means RLS enforces that user_id must equal auth.uid().
5
Flask: _maybe_record_pb()
Queries personal_bests for current best, compares, inserts a new PB row if beaten. Best-effort — exceptions are swallowed.
6
Flask returns the saved solve object
The full row (with DB-generated id and created_at) is returned as JSON.
7
SolveSession updates state — three simultaneous updates
setSolves(prev => [savedSolve, ...prev]) prepends to the main list. The circular buffer gets push(savedSolve). Binary search runs to insert the time into sortedTimes and compute the percentile. React batches all three state updates into a single re-render.
8
Components re-render with new data
SolveLog gets the new solves array. SolveHub gets updated stats and the percentile. A new scramble is generated (the key prop on Scramble changes when solves.length changes, unmounting and remounting the Scramble component).

Frontend Architecture

Component hierarchy, state ownership, and data flow

Component Tree

App.js ── session state (Supabase onAuthStateChange) ├── Auth.js ── rendered when no session └── SolveSession.js ← THE ORCHESTRATOR — owns all app state │ ├── [state] solves, scramble, puzzleType, nextCursor ├── [state] sortedTimes, lastPercentile, pbHistory ├── [hook] useCircularBuffer(12) → recentSolves │ ├── Header.js ← puzzle type selector, logout │ props: type, handleTypeChange │ ├── Timer.js ← spacebar/touch timer, self-contained │ props: onSolveComplete │ owns: isRunning, isReady, time (display), timeRef (actual) │ ├── Scramble.js ← cubing.js scramble generation │ props: type, onScrambleGenerated │ key={`${puzzleType}-${solves.length}`} ← remounts on each solve │ ├── SolveHub.js ← stats summary + charts │ props: solves, recentSolves, pbHistory, lastPercentile │ └── SolveLog.js ← scrollable solve list + inline stats props: solves, onSolveUpdate, onSolveDelete, onReset, onLoadMore, hasMore, isLoadingMore

Why SolveSession is the orchestrator

Single source of truth — React's data model is unidirectional: data flows down through props, events flow up through callbacks. SolveSession owns the solves array, and both SolveLog and SolveHub receive it as a prop. If each component fetched its own data, you'd have two arrays that could get out of sync (one showing 5 solves, the other showing 6 after a delete).

The tradeoff is prop drilling — passing data through components that don't use it themselves just to get it to a child. Here, the tree is two levels deep at most, so this is fine. The threshold for adding a Context or a state manager (Redux, Zustand) is typically when prop drilling goes 4+ levels deep, or when unrelated components at the same level need the same state.

The Scramble Key Trick

// Forces Scramble to unmount and remount on each new solve <Scramble key={`${puzzleType}-${solves.length}`} type={puzzleType} onScrambleGenerated={handleScrambleGenerated} />

When React sees a component's key change, it unmounts the old instance and mounts a fresh one. Scramble.js generates a scramble in a useEffect that runs on mount. So changing the key is the cleanest way to trigger a new scramble after each solve — no imperative "generate new scramble" call needed. This is an idiomatic React pattern.

useCallback and useMemo — Why They Matter Here

useCallback memoizes a function — it returns the same function reference across renders unless its dependencies change. This matters when a function is passed as a prop to a child: without memoization, the function is a new reference on every render, causing the child to re-render unnecessarily.

useMemo memoizes a computed value — the Ao5/Ao12/mean/bestSingle block in SolveLog and the stat block in SolveHub only recompute when solves changes, not on every render caused by unrelated state updates.

Talking Point
"SolveSession is the single source of truth — it owns all solve state and passes it down. Callbacks flow back up. This keeps data consistency guaranteed: you can't have a stale count in one component and a fresh list in another. I used useCallback on all event handlers so their references are stable across renders, and useMemo for all derived stat computations so they only run when the solves array actually changes."

Backend Architecture

Flask as an authenticated proxy — Blueprint, App Factory, and why

The Authenticated Proxy Pattern

Flask's job is narrow and well-defined: validate the JWT, run validation and rate-limiting, then forward the request to Supabase using the user's own token. It doesn't own a database connection pool, doesn't manage schema migrations, and doesn't store session state. It is a stateless processing layer.

Why not call Supabase directly from the frontend? For reads with RLS, you technically could. But for writes, you need server-side validation — the frontend can be tampered with. Also, rate limiting needs to happen server-side. The backend gives you a single, auditable point where every request is inspected before it reaches the database.

Flask Application Factory

# app/__init__.py — the factory function def create_app(config_class=Config): app = Flask(__name__) CORS(app, ...) # cross-origin headers limiter.init_app(app) # rate limiter wired in here app.register_blueprint(solves, url_prefix='/api') return app

The Application Factory pattern creates the Flask app inside a function instead of at module level. Why? Two reasons:

  • Testing — you can call create_app(TestConfig) to create an isolated test instance with a different config, no database side effects.
  • Extension initialization — extensions like Flask-Limiter support init_app() so they can be instantiated before the app exists (avoiding circular imports) and wired in later.

Blueprint for Route Organization

solves = Blueprint('solves', __name__) # All registered together and mounted at /api prefix app.register_blueprint(solves, url_prefix='/api')

A Blueprint is Flask's way of grouping related routes. If this app grew to include a leaderboard, a friends system, or a competition mode, each would become its own Blueprint — clean separation without a monolithic routes file.

The Supabase Client Per Request

def get_supabase_client(access_token=None): client = create_client(url, key) if access_token: client.postgrest.auth(access_token) # ← user-scoped return client

A new Supabase client is created on every request, scoped to the user's token. This is intentional — each request must run as that specific user so that Supabase's RLS policies see auth.uid() as the correct user ID. Sharing a single global client would mean all requests run as the service role (bypassing RLS entirely). The per-request cost is negligible — create_client just constructs an HTTP client with the right headers.

CORS Configuration — and the Bug We Fixed

CORS (Cross-Origin Resource Sharing) is a browser mechanism that requires the server to explicitly allow requests from other origins. Our frontend (localhost:3000) calls our backend (localhost:5000) — different ports, different "origins."

The original code had @cross_origin() decorators on individual routes. This caused a subtle bug: placing @cross_origin() above @blueprint.route() in the decorator stack set provide_automatic_options = False on the already-registered view. Flask then routed browser preflight OPTIONS requests directly to the view function — which hit require_auth and returned 401. The fix: remove all per-route decorators and rely solely on the app-level CORS(app, ...) in create_app.

Talking Point
"The backend is a stateless authenticated proxy — it validates the JWT on every request, runs validation and rate limiting, then forwards to Supabase using the user's own token so row-level security still applies at the database. A new Supabase client is created per request rather than shared globally, because using a global service-role client would bypass RLS entirely."

Database Design

Schema decisions, RLS, and why relational beats NoSQL here

The solves table

CREATE TABLE solves ( id uuid DEFAULT gen_random_uuid() PRIMARY KEY, user_id uuid REFERENCES auth.users NOT NULL, puzzle_type text NOT NULL, -- '333', '444', 'pyram', etc. time numeric NOT NULL, -- seconds, e.g. 12.47 dnf boolean DEFAULT false, -- Did Not Finish plus_two boolean DEFAULT false, -- +2 second penalty scramble text DEFAULT '', created_at timestamptz DEFAULT now() NOT NULL );

UUID primary key vs. sequential integer: UUIDs are unguessable — you can't enumerate other users' solve IDs by incrementing a number. They're also safe to generate client-side if needed. The tradeoff is larger index size and slightly slower B-tree operations (16 bytes vs 4). For this table size, negligible.

numeric for time vs. float: numeric is exact decimal arithmetic in PostgreSQL. float has floating point precision errors (12.47 might become 12.469999999...). For times displayed to the user, exact values matter.

Row Level Security — The Database Enforces Access Control

ALTER TABLE solves ENABLE ROW LEVEL SECURITY; -- Users can only SELECT rows where user_id = their own auth.uid() CREATE POLICY "Users can view own solves" ON solves FOR SELECT USING (auth.uid() = user_id); -- Same for INSERT — the check ensures user_id in the payload matches CREATE POLICY "Users can insert own solves" ON solves FOR INSERT WITH CHECK (auth.uid() = user_id);

RLS is enforced by the PostgreSQL engine itself — not by application code. This means even if there's a bug in Flask that accidentally passes the wrong user_id, the database will reject it. Even if someone bypasses Flask entirely and calls the Supabase PostgREST API directly with a valid JWT, they still can't read another user's solves.

Defense in depth: Access control is enforced at three independent layers — (1) the Supabase JS client only works when logged in, (2) Flask's require_auth validates the JWT and scopes queries to the user, (3) PostgreSQL RLS physically prevents cross-user data access at the row level. A vulnerability in any single layer doesn't compromise the data.

personal_bests — A Materialized Derived Table

CREATE TABLE personal_bests ( id uuid PRIMARY KEY, user_id uuid REFERENCES auth.users, puzzle_type text, time numeric, -- the PB time achieved_at timestamptz, -- when it happened solve_id uuid REFERENCES solves(id) ON DELETE SET NULL );

This is a write-time materialized view — data that could be computed from solves but is instead stored pre-computed for fast reads. Every time a new solve is inserted, the backend checks if it's a PB and appends to this table. The chart query is then a simple indexed scan instead of a full-table scan + running minimum.

Indexes

-- Supports cursor pagination: WHERE user_id=X AND puzzle_type=Y AND created_at < cursor CREATE INDEX solves_user_puzzle_created_idx ON solves (user_id, puzzle_type, created_at DESC); -- Supports PB history chart: WHERE user_id=X AND puzzle_type=Y ORDER BY achieved_at CREATE INDEX personal_bests_user_puzzle_time_idx ON personal_bests (user_id, puzzle_type, achieved_at ASC);

A composite index is useful when your WHERE clause filters on multiple columns. PostgreSQL can use the index for the first column(s) in order, then filter on the rest. The column order matters: put the most selective column first. user_id comes first because filtering by user is always the first thing that happens.

Talking Point
"I chose Supabase over Firebase because the data is fundamentally relational — solves belong to users, have puzzle types, and you want queries like 'minimum time by puzzle type.' That's a SQL-native question. PostgreSQL's row-level security also means the database enforces data ownership independent of the application layer, which is a much stronger security guarantee than application-level access control. I also explicitly chose numeric over float for solve times to avoid floating-point precision errors in displayed values."

Why Bearer tokens prevent CSRF: CSRF (Cross-Site Request Forgery) works by tricking a victim's browser into making a request to your API while the victim is logged in — the browser automatically includes cookies. An attacker's evil website can't access localStorage from another origin (same-origin policy). So CSRF is structurally impossible with Bearer token auth.

The Timer: useState vs. useRef

Why a high-precision timer can't rely on React state alone

The Stale Closure Problem

The timer runs with setInterval every 10ms. But when stopTimer fires, it needs the actual current time — not the time as of the last render. This is the stale closure problem:

// ❌ Naive approach — stale closure bug const [time, setTime] = useState(0); const stopTimer = useCallback(() => { onSolveComplete(time / 1000); // 'time' is captured from the closure at // useCallback creation time — may be stale! }, [time]); // adding 'time' to deps causes stopTimer to recreate every 10ms

If time is in the dependency array, stopTimer becomes a new function every 10ms (as time increments). The keydown event handler holds a reference to the old stopTimer, so it may read a stale value.

The Fix: useRef for Mutable Synchronous Values

// ✓ Correct approach — ref is always current const [time, setTime] = useState(0); // for DISPLAY only const timeRef = useRef(0); // for COMPUTATION // In setInterval: update BOTH setInterval(() => { setTime(prev => { const next = prev + 10; timeRef.current = next; // ref updated synchronously, always current return next; }); }, 10); // stopTimer reads the ref — always accurate, no stale closure const stopTimer = useCallback(() => { onSolveComplete(timeRef.current / 1000); // ← always the real current time }, [onSolveComplete]); // no 'time' dependency needed

The key insight: useRef returns a mutable container whose .current property does not cause re-renders when changed, and is never captured by closures — every read of timeRef.current gets the actual current value. useState is for values that should trigger UI updates. useRef is for values you need to read imperatively from event handlers and callbacks.

Touch Events

The timer also supports touch — onTouchStart for ready state, onTouchEnd to start/stop — making the app usable on phones and tablets. e.preventDefault() prevents the browser from also firing synthetic mouse events on touch (which would double-fire the handler).

Talking Point
"The timer needs to capture the exact elapsed milliseconds at the moment the user releases the key. The naive approach of reading the time from useState hits React's stale closure problem — the stopTimer callback captures the time value from its creation closure, which might be 10-100ms stale. The fix is to maintain a useRef that's updated synchronously inside the setInterval callback. Refs are not captured by closures — reading timeRef.current always gives the actual current value. useState still drives the display (it re-renders the visible timer), while useRef drives the computation."

State Management Strategy

Why there's no Redux or Zustand — and when you'd add one

Why useState + prop drilling is correct here

The state in this app lives in one component (SolveSession) and is consumed by its direct children. The prop drilling is at most two levels deep. Every state update is triggered by a user action (solve complete, delete, update) or a data fetch.

The rule of thumb: Add a state manager when (a) you're drilling props more than 3-4 levels deep, (b) unrelated components at the same level need the same state and prop drilling would require threading through components that don't care about the data, or (c) you need time-travel debugging or complex action patterns. None of these apply here.

What each state variable owns

StateLives inWhy there
solvesSolveSessionBoth SolveLog and SolveHub need it — nearest common ancestor
puzzleTypeSolveSessionDrives both API fetches and scramble generation
scrambleSolveSessionSet by Scramble, consumed when a solve is saved
sortedTimesSolveSessionMaintained alongside solves; drives percentile computation

If the app grew — what would change first?

If you added a leaderboard or friends list that needed user data in a sidebar component unrelated to SolveSession, you'd reach for React Context first (lightweight, built-in). If actions got complex (optimistic updates, rollback on failure, offline queue), Zustand's simple store model would fit before Redux's ceremony is warranted.

How to walk someone through this project in 3-5 minutes

Opening (30 seconds)

"Ao5 is a speedcubing timer app — it's fully full-stack: a React frontend, a Flask backend acting as an authenticated proxy, and Supabase as the hosted PostgreSQL database. Users log in, solve puzzles with the spacebar, and their times are saved with rolling stats like Ao5 and Ao12, a personal best progression chart, and a live percentile rank after each solve."

Architecture (60 seconds)

"The architecture is three layers. The React frontend handles all the UI and talks to Flask over HTTP. Flask's only job is to validate the JWT on every request, run input validation and rate limiting, then forward the query to Supabase using the user's own token. By forwarding the user's token instead of a service-role token, Supabase's row-level security still applies at the database engine level — so even a bug in Flask couldn't expose another user's data. Auth is handled directly between the browser and Supabase — Flask isn't in the login flow at all."

Interesting engineering decisions (90 seconds)

"A few things I'm particularly happy about: First, the timer uses a useRef alongside useState — useState drives the display, but the ref captures the exact time at stop because React closures can go stale in a 10ms interval loop. Second, I replaced an O(n²) rolling average bug with a sliding window — the original code was slicing the entire remaining array on each iteration to use only 5 elements. Third, I replaced a naive full-table load with cursor-based pagination using a composite B-tree index — offset pagination re-scans all prior rows and produces duplicates under concurrent writes, both of which get worse as solve count grows. Fourth, personal best history uses write-time materialization — instead of scanning all solves on every chart load, I record a row in a personal_bests table at insert time if a new PB is set. The read is then O(1). This is the CQRS pattern."

Technology choices (45 seconds)

"I chose React CRA over Next.js because every page requires authentication — SSR provides zero benefit when there's nothing to prerender. Flask over Django because this backend is a thin proxy, not a full application framework — I don't need an ORM, admin panel, or form handling. Supabase over Firebase because the data is relational, and I wanted SQL-level row security enforced by the database engine rather than application code. And client-side scramble generation with cubing.js so there's no server round-trip before the user can start timing."

If they push further — what would you do differently?

"A few things I'd tackle next: add a Redis cache for the stats endpoint so that GET /stats doesn't recompute on every load for users with large solve counts — with a 30-second TTL and invalidation on writes. I'd also move the rate limiter key from IP address to user ID, since behind a NAT multiple users can share an IP. And I'd add optimistic updates on the frontend so the solve appears in the list immediately while the API call is in flight — better perceived performance."
