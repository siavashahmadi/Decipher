SD-4

Input Validation — Defense at the System Boundary

backend/app/validators.py · Security · Small scope

The principle: validate at system boundaries

A system boundary is any point where data crosses from an untrusted source into your controlled system: HTTP request bodies, file uploads, message-queue payloads, webhook bodies. Internal function calls between your own code do not need defensive validation. The HTTP layer is a boundary; you cannot trust what arrives there even if the request is authenticated.

Why authenticated does not mean trusted: Authentication answers "who are you?" not "is your payload valid?" A logged-in user can still send malformed data accidentally (a client bug) or deliberately (API abuse).

What was built

validators.py exports pure functions with zero framework dependencies:

def validate_create_solve(data: dict) -> dict | None: errors = {} puzzle_type = data.get('puzzle_type') if puzzle_type not in VALID_PUZZLE_TYPES: # allowlist errors['puzzle_type'] = "Must be one of: 222, 333, ..." time = data.get('time') if isinstance(time, bool) or not isinstance(time, (int, float)): errors['time'] = "Must be a number" elif time < 0.1 or time > 3600: errors['time'] = "Must be between 0.1 and 3600 seconds" if len(data.get('scramble', '')) > 500: errors['scramble'] = "Must be 500 characters or fewer" return errors if errors else None

The PATCH allowlist

validate_update_solve accepts dnf and plus_two only. The route then strips the payload to those two fields before passing to Supabase, so even a malicious client cannot overwrite immutable fields like user_id or time:

allowed = {k: data[k] for k in ('dnf', 'plus_two') if k in data} # Audit A.6: empty PATCH bodies return 400 to close an existence-oracle if not allowed: return error_response(VALIDATION_FAILED, "Body must include dnf or plus_two", 400) result = supabase.table('solves').update(allowed)...

The bool subclass trap

In Python, bool is a subclass of int: isinstance(True, int) is True. Without the explicit bool check first, True would pass as a valid time value of 1 and False as 0.

Cursor format validation

The cursor parameter is user-supplied and gets interpolated into a PostgREST .or_() filter. Strict regex validation in _decode_solve_cursor (audit B-era hardening) rejects anything that is not a plain ISO-8601 timestamp plus UUID, preventing any chance of breaking out of the intended filter shape.

Resume Talking Point
"I implemented input validation at the HTTP boundary using an allowlist approach (explicitly enumerate valid puzzle types) over a blocklist. Returns 422 with field-level error messages following the same convention as Stripe's API. The PATCH handler strips the payload to only the fields allowed to change, preventing clients from overwriting immutable fields. Empty PATCH bodies return 400 to close an existence-oracle vulnerability."

Sliding Window — O(n²) → O(n) Rolling Averages

frontend/src/utils/averages.ts · Algorithms · Small scope

The original bug

The solve log shows an Ao5 next to every solve in the list. The original code computed this with a .map() loop that sliced the entire remaining array on each iteration:

// OLD — O(n²) solves.map((_, index) => calculateAverage(solves.slice(index), 5) // slice copies (n-i) elements )

Why O(n²)? Array.slice(i) copies n-i elements. Summed across the loop:

n + (n-1) + (n-2) + ... + 1 = n(n+1)/2 = O(n²) With 500 solves: 500 × 501 / 2 = 125,250 element copies With 1000 solves: 1000 × 1001 / 2 = 500,500 element copies

The fix: fixed-size window

calculateAverage only ever uses 5 elements. Slice exactly that many:

// NEW — O(n) solves.map((_, index) => calculateAverage(solves.slice(index, index + 5), 5) // always copies exactly 5 )

Each iteration does O(5) = O(1) work. The entire .map() is O(n).

Sliding window concept

Solves array (newest first): [8.2, 9.1, 7.5, 10.2, 8.8, 9.3, 7.9, ...] └──────────────────┘ window at index 0 (Ao5 for solve #1) └──────────────────┘ window at index 1 (Ao5 for solve #2)
ApproachTime per render500 solvesNotes
Original (slice tail)O(n²)~125K opsCopies grow with n
Fixed window slice (current)O(n)~2,500 opsAlways copies 5
Sum + monotonic dequeO(n)~500 opsO(1) per step; complexity not worth it for window of 5

Memoization layer

The result is wrapped in useMemo in SolveLog (and now precomputed in useSortedSolveStats when the audit's C.5 virtualizer landed). It only recomputes when solves changes, not on every render caused by unrelated state updates.

Resume Talking Point
"I identified an O(n²) bug in the rolling-average computation: for each of n solves, it was slicing the entire remaining array to extract just 5 elements. Fixed to a sliding window that slices exactly the 5-element window at each position, reducing total allocations from O(n²) to O(n). The useMemo wrapper means it only runs when solves changes."
SD-2

Cursor-Based Pagination + (created_at, id) Tiebreaker

backend/app/routes/solves.py · queries/solves.ts · Medium scope

Why not load everything

The original GET /api/solves returned every solve for a user. A dedicated speedcuber accumulates 10,000+ solves easily. Returning all of them on every page load means large JSON payloads, full-table scans, React holding the entire dataset in memory, and the O(n) and O(n²) operations getting worse over time.

Why not offset pagination

Problem 1: Offset re-scans rows SELECT * FROM solves ORDER BY created_at DESC LIMIT 50 OFFSET 500 Postgres scans and discards 500 rows to reach row 501. Gets slower as you page deeper. Problem 2: Offset breaks under concurrent writes Page 1: rows [1, 2, 3, 4, 5] returned ← user reads this ↓ another solve is inserted at position 1 Page 2 (OFFSET 5): rows [5, 6, 7, 8, 9] returned ← row 5 appears TWICE row 1 was pushed down and is now MISSING from page 1

Cursor pagination — the right approach

# First page GET /api/v1/solves?puzzle_type=333&limit=50 # Response { "solves": [...50 solves...], "next_cursor": "MjAyNi0wNC0yOVQyMjozMjoxMS4wMDBafGFiYy0xMjM..." // b64url("created_at|id") } # Next page GET /api/v1/solves?puzzle_type=333&limit=50&cursor=<next_cursor>

The (created_at, id) tiebreaker — D.9

Without a tiebreaker, two solves with identical microsecond timestamps (rare under normal use; possible under bulk inserts or migrations) drop a row across pages. The cursor is now base64url("created_at|id"); the WHERE clause uses an OR with the tiebreaker:

# Postgres-side query SELECT * FROM solves WHERE user_id = $1 AND puzzle_type = $2 AND deleted_at IS NULL -- soft-delete filter AND (created_at < $cursor_ts OR (created_at = $cursor_ts AND id < $cursor_id)) ORDER BY created_at DESC, id DESC LIMIT 50;

The decoder still accepts the legacy timestamp-only shape for one release window; after stale cursors rotate out (~30 days of normal use), the legacy branch can be removed.

The partial composite index — D.1

CREATE INDEX solves_user_puzzle_created_active_idx ON solves (user_id, puzzle_type, created_at DESC) WHERE deleted_at IS NULL;

The WHERE deleted_at IS NULL predicate makes this a partial index. The query plan no longer needs a Filter row to recheck soft-delete state. EXPLAIN shows an Index Scan with no recheck.

Frontend: TanStack Query handles pagination

The full-list query in queries/solves.ts loops through pages until next_cursor is null or the cap is hit (200 pages × 50 rows = 10,000 solves max). Switching puzzles cancels in-flight requests via the AbortSignal threaded through axios.

const fetchAllAuthSolves = async (puzzleType, signal) => { const all = []; let cursor = null; let pages = 0; do { const page = await api.getSolves(puzzleType, cursor, signal); all.push(...page.solves); cursor = page.next_cursor; pages++; if (pages >= MAX_PAGES) break; } while (cursor); return { solves: all, truncated: pages >= MAX_PAGES && cursor !== null }; };
Resume Talking Point
"I replaced a full-table load with cursor-based pagination. The cursor encodes (created_at, id) so identical-timestamp inserts cannot drop a row across pages. The composite index on (user_id, puzzle_type, created_at DESC) WHERE deleted_at IS NULL is partial, so the query plan does not need a recheck row for the soft-delete filter. On the frontend, TanStack Query loops pages until done or capped at 10,000, with AbortSignal threaded through axios so puzzle switches cancel in-flight requests."
DSA-2

Binary Search — O(log n) Percentile After Each Solve

frontend/src/hooks/useSortedSolveStats.ts · Algorithms · Medium scope

The feature

After each solve, the SolveHub shows a percentile: "Faster than 73% of your solves." This requires knowing how the new time ranks among all previous times.

The naive approach

Re-sort all solves every time. With 1,000 solves: O(n log n) per solve. Over 1,000 solves: O(n² log n) total work.

The right approach: maintain a sorted copy

Keep a sorted copy of all valid times alongside the main solves array. On each new solve, insert it into the sorted copy in the right position using binary search — O(log n) to find, O(n) to splice. Standard sorted-insertion maintenance.

// bisectLeft: leftmost index where val can be inserted to keep arr sorted const bisectLeft = (arr: number[], val: number): number => { let lo = 0, hi = arr.length; while (lo < hi) { const mid = (lo + hi) >> 1; if (arr[mid]! < val) lo = mid + 1; else hi = mid; } return lo; };

The non-null assertion on arr[mid]! is required by noUncheckedIndexedAccess; the binary-search invariant guarantees it is safe.

The percentile formula

// pos = number of previous solves FASTER than this one // beaten = number of previous solves SLOWER than this one const pos = bisectLeft(prev, time); const beaten = prev.length - pos; const pct = Math.round((beaten / prev.length) * 100);

Where this lives

Audit E.9 extracted this logic from the monolithic useSolveSession into useSortedSolveStats:

const useSortedSolveStats = () => { const sortedTimesRef = useRef<number[]>([]); const [lastPercentile, setLastPercentile] = useState<number | null>(null); const medianTracker = useMedianTracker(); return { sortedTimesRef, lastPercentile, currentMedian: medianTracker.getMedian(), applySolveAdded(time: number): void { /* binary insert + percentile + median push */ }, applySolveRemoved(time: number): void { /* splice + median rebuild */ }, rebuildFrom(times: number[]): void { /* full rebuild from a fresh fetch */ }, }; };

Why bisectLeft over bisectRight

bisectLeft places the new element before any existing equal elements. The conservative choice — if your time ties an existing solve, it does not inflate your percentile.

OperationRe-sort approachBinary search + sorted copy
Find positionO(n log n)O(log n)
Insert elementO(n log n)O(n) splice
Total per solveO(n log n)O(log n) find + O(n) insert
After 1,000 solves totalO(n² log n)O(n²) — fast in practice
Why a separate sorted array instead of sorting solves in place? The main solves array is displayed in reverse-chronological order (newest first). Sorting it in place destroys display order. A separate sorted copy is a classic space-for-time tradeoff: 2x memory, O(log n) lookup instead of O(n log n) sort.
SD-3

Personal Best History — Atomic Postgres RPC (CQRS Lite)

migrations/003, 010, 011 · services/solves_service.py · SolveHub.tsx

The feature

A chart showing how your personal best (PB) for a puzzle improved over time. Answers: "How has my 3x3 PB improved over the past 6 months?"

Compute on read vs. compute on write

Option A — Compute on READ (every request) GET /personal-bests → SELECT MIN(time) FROM solves WHERE user_id=X AND puzzle_type=333 → For history we'd scan ALL solves in order, track running minimum, emit a row each drop. → O(n) scan, every request. 10,000 solves means 10,000 rows scanned per page load. Option B — Compute on WRITE (current implementation) POST /solves (new solve arrives) → Insert solve ✓ → Atomically: if time < current PB, insert one row into personal_bests GET /personal-bests → SELECT * FROM personal_bests WHERE user_id=X AND puzzle_type=333 ORDER BY achieved_at → O(1) index scan regardless of solve count
The CQRS principle in miniature. Commands (writes) pay a small extra cost to maintain derived state. Queries (reads) pay almost nothing. personal_bests is a write-time materialized view, kept up-to-date on every write.

The atomic RPC — D.8

The original implementation was a read-then-insert pattern (two round-trips, no transaction). Concurrent solves could race to insert duplicate PB rows for ties. The fix was a Postgres function:

CREATE FUNCTION record_pb_if_better( p_user_id uuid, p_puzzle_type text, p_solve_id uuid, p_time numeric ) RETURNS void AS $$ BEGIN INSERT INTO personal_bests (user_id, puzzle_type, time, achieved_at, solve_id) SELECT p_user_id, p_puzzle_type, p_time, now(), p_solve_id WHERE NOT EXISTS ( SELECT 1 FROM personal_bests WHERE user_id = p_user_id AND puzzle_type = p_puzzle_type AND time <= p_time -- already at or below this time? skip insert ); END; $$ LANGUAGE plpgsql SECURITY INVOKER;

One round-trip, atomic. The SECURITY INVOKER means it runs as the calling user, so RLS still applies.

Service-side call

class PersonalBestsRepository: def record_pb_if_better(self, user_id, puzzle_type, solve_id, time): self.supabase.rpc('record_pb_if_better', { 'p_user_id': user_id, 'p_puzzle_type': puzzle_type, 'p_solve_id': solve_id, 'p_time': time, }).execute()

Batch migration: recompute_pbs_for_user — D.7

When a guest signs up, the batch endpoint inserts up to 1,000 solves in one transaction. PBs cannot be incrementally maintained because the solves arrive out of natural insertion order. Migration 011 adds a second RPC that wipes and rebuilds PB rows from scratch in chronological order:

CREATE FUNCTION recompute_pbs_for_user(p_user_id uuid) RETURNS void AS $$ BEGIN DELETE FROM personal_bests WHERE user_id = p_user_id; INSERT INTO personal_bests (user_id, puzzle_type, time, achieved_at, solve_id) SELECT user_id, puzzle_type, time, created_at, id FROM ( SELECT user_id, puzzle_type, time, created_at, id, min(time) OVER (PARTITION BY puzzle_type ORDER BY created_at, id) AS running_min FROM solves WHERE user_id = p_user_id AND deleted_at IS NULL AND NOT dnf ) ranked WHERE time = running_min; END; $$ LANGUAGE plpgsql SECURITY INVOKER;

Tradeoffs

ConcernImpactDecision
Race conditionsTwo concurrent solves race for a PBAtomic RPC eliminates the race
StorageOne row per PB eventTiny — most users have < 100 PBs ever
PB after solve deleteDeleted PB row stays referenced if solve_id is set nullsolve_id ON DELETE SET NULL; chart is historical, not live

Resume Talking Point
"I chose write-time PB materialization over read-time computation. GET /personal-bests is an O(1) indexed query regardless of solve count. The original implementation was a read-then-insert pattern with a TOCTOU race; I replaced it with an atomic Postgres function that inserts only if no equal-or-better PB exists. For the batch guest-migration path, a separate RPC wipes and rebuilds PB rows in chronological order from a window-function query, since incremental maintenance does not work when solves arrive out of order."

Circular Buffer — O(1) Fixed-Window Tracking

frontend/src/lib/circularBuffer.ts · Data Structures · Small scope

What is a circular buffer

A circular buffer (ring buffer) is a fixed-capacity array that reuses its own storage. When full, the next write overwrites the oldest element. Two pointers (head and size) are all you need to track state.

Buffer of capacity 5, after pushing [A, B, C, D, E]: index: [ 0 1 2 3 4 ] items: [ A B C D E ] ↑ head=0 (wraps back to start) Push F: items: [ F B C D E ] ← A is overwritten ↑ head=1 toArray() reads from head → head+size, wrapping: [B, C, D, E, F] ✓

Why O(1) push matters

OperationArray.push + sliceCircular Buffer
Add item to endO(1)O(1)
Evict oldest (keep last N)O(n) — splice or sliceO(1) — overwrite slot, move head
Read all itemsO(n)O(n)
Memory allocationNew array on every evictionFixed array, reused

For a window of 12, the absolute difference is small. The circular buffer teaches the concept used in real systems everywhere: OS kernel network receive buffers, audio playback buffers, log rotation, the Linux kernel's kfifo.

Where it is used: The recent-12 chart in SolveHub. Solve arrivals push to the buffer in O(1); the chart reads via toArray() wrapped in a useMemo gated on the solves array.

Per-User Token Bucket Rate Limiting

backend/app/extensions.py · routes/solves.py · Security · Small scope

Why rate limit

Without rate limiting, any authenticated user can hammer the API — intentionally or from a client bug running in a loop. A tight loop of POST /solves could insert thousands of rows per minute, inflating storage and compute costs.

Three common algorithms

AlgorithmHow it worksBurst behaviorComplexity
Fixed Window Count requests in a fixed time bucket; reset at boundary Allows 2x burst at window boundary O(1)
Sliding Window Log Store timestamp of every request, count in past N seconds Exact O(requests) storage
Token Bucket (current) Bucket of C tokens, refills at R/sec; each request consumes 1 Allows bursts up to C, then enforces R O(1) time, O(1) storage

Per-user keying — B.10

Originally the limiter keyed on IP address. Two problems: (1) corporate NATs share an IP across users; (2) attackers can rotate IPs. Audit B.10 changed the key function:

# extensions.py from flask import g from flask_limiter import Limiter from flask_limiter.util import get_remote_address def _user_or_ip_key(): user_id = getattr(g, 'user_id', None) return user_id or get_remote_address() limiter = Limiter( key_func=_user_or_ip_key, storage_uri=os.environ.get("LIMITER_STORAGE_URI", "memory://"), # B.11: swappable )

Authenticated routes key on user (require_auth runs first and sets g.user_id). Unauthenticated routes (auth, share read) key on IP. Users behind a corporate NAT no longer share quota with each other.

Per-route limits

@solves.route('/solves', methods=['GET']) @require_auth @limiter.limit("60 per minute") def get_solves(): ... @solves.route('/solves', methods=['POST']) @require_auth @limiter.limit("30 per minute") def create_solve(): ... @solves.route('/solves/batch', methods=['POST']) @require_auth @limiter.limit("5 per minute") # tighter; batch up to 1000 rows each def create_solves_batch(): ...

Storage swappable

Default is memory:// (in-process). For multi-worker deployments where the same user can hit different workers and effectively get N x quota, set LIMITER_STORAGE_URI=redis://... in the host's env. No code change.

Resume Talking Point
"Rate limiting uses the token bucket algorithm — 30/min POST, 60/min GET. Token bucket beats fixed window because fixed window allows a 2x burst at the window boundary. The audit changed the key function from IP to user ID, with IP fallback for unauthenticated routes — corporate NAT users no longer share quota and IP rotation no longer evades the limit. Storage URI is env-driven so a multi-worker deployment can swap from in-memory to Redis without a code change."

WCA Inspection Timer — Phase State Machine

frontend/src/hooks/useTimerMachine.ts · UX · Medium scope

The feature

WCA regulations give competitors 15 seconds of inspection before each solve. During inspection you can look at the cube; the solve clock starts when you touch the timer. Exceeding 15 seconds applies a +2 penalty.

The boolean trap

The original Timer used isRunning + isReady. Two booleans = 4 combinations (3 valid, 1 illegal). Adding inspection as a third boolean = 8 combinations (4 illegal). Bugs emerge when you forget to guard one of them.

The phase enum FSM

State machine: IDLE ──(space down)──> READY ──(space up)──> INSPECTION ──(space down)──> RUNNING ^ │ └──────────────────────────────(space down)─────────────────────────────────────┘ INSPECTION: countdown ticks 15 → 0 (gated to displayed-second changes) RUNNING: RAF loop writes elapsed ms to DOM textContent (zero React commits) Transition RUNNING → IDLE: read timeRef.current, fire onSolveComplete

The hook extraction — E.10

Audit E.10 extracted all timer logic from the component into hooks/useTimerMachine.ts. Component became a 60-line presentational shell. The pure helper tickInspection(elapsed): 'continue' | 'expired' is also extracted and unit-tested in isolation.

Stale-closure problem

React event handlers registered in useEffect capture state values at the time the effect runs. The fix is a phaseRef mutated synchronously alongside the state update:

const phaseRef = useRef<Phase>('idle'); const [phase, setPhase] = useState<Phase>('idle'); const setPhaseSync = (next: Phase) => { phaseRef.current = next; setPhase(next); }; const handleKeyDown = (event: KeyboardEvent) => { const p = phaseRef.current; if (p === 'idle') setPhaseSync('ready'); else if (p === 'inspection') startRunning(); else if (p === 'running') finishSolve(); };

Inspection countdown — gated ticks (C.2)

const lastShownSecondRef = useRef(15); const startInspection = useCallback(() => { inspectionStartRef.current = performance.now(); setInspectionCount(15); inspectionIntervalRef.current = setInterval(() => { const elapsed = performance.now() - inspectionStartRef.current; const remaining = Math.max(0, Math.ceil((15000 - elapsed) / 1000)); if (remaining !== lastShownSecondRef.current) { lastShownSecondRef.current = remaining; setInspectionCount(remaining); // only when displayed second changes } }, 250); setPhaseSync('inspection'); }, []);

Polls every 250ms but only re-renders when the visible second changes. ~4 renders per visible second instead of 10/s.

RAF + textContent during running phase — C.1

The naive approach calls setTime 60x/sec. The current approach writes directly to a DOM ref so React commits zero times during a 5-10 second solve. Profiler shows a flat flame graph between phase transitions.

DSA-4

Two-Heap Running Median — O(log n) per Push, O(1) Query

frontend/src/hooks/useMedianTracker.ts · Data Structures · Medium scope

The problem

Average is skewed by outliers. The median is more robust. A speedcuber's median time is a truer reflection of their typical solve.

Why not just sort

Sorting all times on every new solve is O(n log n). Over n solves: O(n² log n).

Two heaps split at the median

lo: max-heap of the lower half (peek = largest of lower half) hi: min-heap of the upper half (peek = smallest of upper half) Invariant: lo.size >= hi.size and lo.size - hi.size <= 1 Times [5.2, 7.8, 9.0, 11.4, 13.1]: lo (max-heap): [9.0, 7.8, 5.2] ← peek = 9.0 hi (min-heap): [11.4, 13.1] odd total → median = lo.peek() = 9.0 Add 10.5: lo: [9.0, 7.8, 5.2] hi: [10.5, 11.4, 13.1] even total → median = (9.0 + 10.5) / 2 = 9.75

Push algorithm

function push(val) { // Route to correct heap if (lo.size === 0 || val <= lo.peek()) lo.push(val); else hi.push(val); // Rebalance if (lo.size < hi.size) lo.push(hi.pop()); if (lo.size - hi.size > 1) hi.push(lo.pop()); } function getMedian() { if (lo.size === 0) return null; return lo.size > hi.size ? lo.peek() : (lo.peek() + hi.peek()) / 2; }

Hand-rolled BinaryHeap

JavaScript has no built-in heap. The hook implements a minimal BinaryHeap<T> class parameterised by a compare function:

const lo = useRef(new BinaryHeap<number>((a, b) => a > b)); // max-heap const hi = useRef(new BinaryHeap<number>((a, b) => a < b)); // min-heap

Stored in refs because mutations should not trigger re-renders. Components consume getMedian() via a memo gated on the solves array (same pattern as DSA-3).

Why two structures for percentile vs median

DSA-2 maintains a sorted array for percentile (rank queries). DSA-4 maintains two heaps for median (middle-element queries). Different query types, different optimal structures, both maintained in parallel inside useSortedSolveStats.

QueryData structureInsertQuery
Percentile rank of new timeSorted array + binary searchO(n) spliceO(log n)
Median of all timesTwo-heapO(log n)O(1)
Median (naive)Re-sortO(n log n)O(1)
Deletion: Heaps don't support efficient arbitrary deletion. On solve delete, the tracker resets and rebuilds from sortedTimesRef in O(n). Acceptable since deletions are rare and user-initiated. For a system with frequent deletes, an order-statistic tree (balanced BST with augmented subtree sizes) would handle median + rank + delete all in O(log n).
SD-6

Optimistic Updates with Rollback — Eventual Consistency at the UI Layer

frontend/src/hooks/useSolveSession.ts · System Design · Small scope

The problem with pessimistic updates

The original handlers waited for the API response before updating the UI. On mobile or slow connections this feels broken: tap, freeze, then update. Especially jarring in a timer app between rapid solves.

Optimistic updates: the pattern

Update UI immediately. If the server returns an error, roll back to the pre-mutation snapshot. Instantaneous for the common path (success), correct for the uncommon path (failure).

// AFTER — optimistic with rollback const snapshot = solves; // capture BEFORE mutation setSolves(prev => prev.map(s => s.id === updated.id ? updated : s)); // immediate try { await api.updateSolve(updated.id, updated); // fire in background invalidateSolveCaches(qc, puzzleType); // tell TanStack Query } catch { setSolves(snapshot); // rollback toast.error('Could not update solve.'); }

Three concepts this demonstrates

Eventual consistency. After the optimistic update, the local UI state and the server state temporarily diverge. The UI has applied the change; the network request is still in flight. Success → both converge. Failure → rollback re-converges.

Idempotency. PATCH and DELETE are safe to use optimistically because they are idempotent. Toggling DNF on a solve that is already DNF (race condition or retry) yields the same result. This is why REST chose these verbs for update/delete.

Snapshot before mutation. Capture the snapshot before the setState, not after. Capturing after means the snapshot already contains the change; "rollback" would not actually restore anything.

Delete with derived-state rollback

const handleSolveDelete = async (solveToDelete) => { const snapshot = solves; const sortedSnapshot = sortedTimesRef.current; const medianSnapshot = medianTracker.snapshot(); setSolves(prev => prev.filter(s => s.id !== solveToDelete.id)); applySolveRemoved(solveToDelete.time); // updates sortedTimesRef + median try { await api.deleteSolve(solveToDelete.id); invalidateSolveCaches(qc, puzzleType); } catch { setSolves(snapshot); sortedTimesRef.current = sortedSnapshot; medianTracker.restore(medianSnapshot); toast.error('Could not delete solve.'); } };

The audit's H.3 work could lift this manual snapshot/rollback pattern into TanStack Query's onMutate/onError lifecycle. The current implementation was deliberately preserved to keep the timer hot path stable; the TODO is in TODO_manual_edits.md.

Standardized Error Envelope — One Shape, Stable Codes

backend/app/errors.py · services/api.ts · Audit H.2

The problem before

Different routes returned different error shapes. Some used {error: "string"}, some used {error: "...", fields: {...}}, some used {message: "..."}. Framework-emitted errors (rate limit 429, missing route 404) returned Flask's HTML error pages or another shape entirely. Frontend had to special-case each.

The unified envelope

{ "error": { "code": "SOLVE_LIMIT_REACHED", // stable upper-snake-case "message": "Solve limit reached", // human-readable "fields": { "time": "Must be > 0" } // optional, present on validation failures } }

Stable codes catalog

backend/app/errors.py exports one constant per error code. Examples: AUTH_MISSING_TOKEN, AUTH_INVALID_TOKEN, AUTH_UNAVAILABLE, VALIDATION_FAILED, SOLVE_LIMIT_REACHED, SOLVE_NOT_FOUND, SHARE_LINK_INVALID, RATE_LIMITED, NOT_FOUND, INTERNAL_ERROR, BATCH_VALIDATION_FAILED, INVALID_QUERY_PARAM.

Codes are switch-on-able: the frontend branches on code for known errors, falls back to message for unknown ones. Adding a new code is additive: existing clients continue to work because they fall back gracefully.

The error_response helper

def error_response(code: str, message: str, status: int, fields: dict | None = None): body = {"error": {"code": code, "message": message}} if fields: body["error"]["fields"] = fields return jsonify(body), status

Framework errors covered too

App-level @app.errorhandler registrations for 404, 429, and 500 route framework-emitted errors through error_response. Every error response on the wire matches the same shape regardless of who raised it:

@app.errorhandler(429) def _handle_rate_limit(_e): return error_response(RATE_LIMITED, "Too many requests, please slow down", 429) @app.errorhandler(404) def _handle_not_found(_e): return error_response(NOT_FOUND, "Resource not found", 404)

Frontend parsing

// services/api.ts interface ApiError { code: string; message: string; fields?: Record<string, string>; } axios.interceptors.response.use( (response) => response, (error) => { const data = error.response?.data; const apiError: ApiError = data?.error ?? { code: 'UNKNOWN', message: error.message ?? 'Unknown error', }; // Re-throw with structured fields so call sites can switch on code throw Object.assign(new Error(apiError.message), { code: apiError.code, fields: apiError.fields }); }, );
Resume Talking Point
"Every 4xx and 5xx response goes through one helper that emits a stable {error: {code, message, fields}} shape. HMAC Share-Link Signing — Stateless Tokens with Embedded TTL

backend/app/services/share_links_service.py · Audit A.7

The original (broken) scheme

The first share-link implementation embedded a 16-byte HMAC alongside the solve UUID in the URL: b64(id).b64(mac). Two problems: (1) no expiry, links lived forever; (2) used the service-role Supabase key on every read with no audit trail.

Current scheme — A.7

Token = b64url(solve_id).b64url(iat).b64url(exp).b64url(mac) │ │ │ │ │ │ │ └── HMAC-SHA256(SHARE_SECRET, "id:iat:exp")[:16] │ │ └── exp unix timestamp (8 bytes BE) │ └── iat unix timestamp (8 bytes BE) └── solve UUID

Sign and verify

def _sign_solve_id(solve_id: str) -> str: iat = _now_seconds() exp = iat + SHARE_TOKEN_TTL_SECONDS # 30 days msg = f"{solve_id}:{iat}:{exp}".encode() mac = hmac.new(_require_share_secret(), msg, hashlib.sha256).digest()[:MAC_LENGTH] return ".".join([ _b64url(solve_id.encode()), _b64url(_pack_int(iat)), _b64url(_pack_int(exp)), _b64url(mac), ]) def _verify_share_token(token: str) -> str | None: try: id_part, iat_part, exp_part, mac_part = token.split(".", 3) solve_id = _b64url_decode(id_part).decode("utf-8") iat = _unpack_int(_b64url_decode(iat_part)) exp = _unpack_int(_b64url_decode(exp_part)) provided = _b64url_decode(mac_part) except (ValueError, UnicodeDecodeError): return None msg = f"{solve_id}:{iat}:{exp}".encode() expected = hmac.new(_require_share_secret(), msg, hashlib.sha256).digest()[:MAC_LENGTH] if not hmac.compare_digest(provided, expected): return None if _now_seconds() > exp: return None return solve_id

hmac.compare_digest — constant-time comparison

A naive provided == expected short-circuits on first byte mismatch. The number of bytes compared leaks information about how close the attacker's guess is. hmac.compare_digest always compares all bytes, so timing reveals nothing about the secret.

SHARE_SECRET length floor — A.7

create_app raises RuntimeError at boot if SHARE_SECRET is shorter than 32 characters. Catches misconfiguration before the first request rather than at first signature verification.

Why stateless

HMAC stateless (current)00Hard cutover onlyEmbedded

Per-link revocation was deferred (A.7 option 2). Today the only revocation lever is rotating SHARE_SECRET, which invalidates every outstanding link. The runbook in docs/share-secret-rotation.md documents the procedure plus a future dual-secret rolling-window pattern (~30 lines of Python) if frequent rotation becomes necessary.

The dangerous_admin module — H.8

The share-read route is the only path that uses the service-role Supabase key (it has to bypass RLS to read another user's solve, after the signature has been verified). The fast/slow split

Fast path: verify_token_local(token) → PyJWT decodes against cached JWKS │ ▼ sub claim → return user_id Slow path (only on fast-path failure): supabase.auth.get_user(jwt=token) → HTTP round-trip │ ▼ user.user.id → user_id + INFO log: "auth_slow_path event=auth_slow_path" (operator-aggregated)

The JWKS singleton — B.3

payload = jwt.decode( token, signing_key.key, algorithms=["ES256", "RS256"], # asymmetric only audience="authenticated", issuer=f"{url}/auth/v1", # B.1: reject tokens from other projects )

Tightened exception handling — B.2

The original except Exception collapsed expired tokens, signature errors, and programmer bugs into one silent None. The audit split this:

When the slow path fires

  1. JWKS unreachable (transient or sustained Supabase outage)
  2. Legacy HS256 tokens (older Supabase projects that haven't rotated to asymmetric keys)

SD-11

Atomic Solve-Lifetime Cap — Counter Table + Trigger

migrations/009_user_stats.sql · Audit A.2 + D.4

The original implementation and its race

The lifetime cap (100,000 solves per user) was originally enforced with a count(*) query before every insert. Two problems:

  1. Slow at scale. count(*) is a sequential scan in Postgres for non-trivial table sizes.
  2. TOCTOU race. Two concurrent inserts both read count = 99,999, both decide they are below the cap, both insert, final count is 100,001.

The counter table

CREATE TABLE user_stats ( user_id uuid PRIMARY KEY REFERENCES auth.users ON DELETE CASCADE, solve_count integer NOT NULL DEFAULT 0 ); CREATE FUNCTION update_user_solve_count() RETURNS trigger AS $$ BEGIN IF (TG_OP = 'INSERT') THEN INSERT INTO user_stats (user_id, solve_count) VALUES (NEW.user_id, 1) ON CONFLICT (user_id) DO UPDATE SET solve_count = user_stats.solve_count + 1; ELSIF (TG_OP = 'UPDATE' AND OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL) THEN UPDATE user_stats SET solve_count = solve_count - 1 WHERE user_id = NEW.user_id; END IF; RETURN NULL; END; $$ LANGUAGE plpgsql; CREATE TRIGGER solves_solve_count_trigger AFTER INSERT OR UPDATE ON solves FOR EACH ROW EXECUTE FUNCTION update_user_solve_count();

Why the trigger fixes the race

The trigger runs inside the same transaction as the insert. The atomic increment via ON CONFLICT DO UPDATE serializes concurrent inserts. The service reads the counter (single index lookup, fast); if it's at the cap, it returns 429 with code SOLVE_LIMIT_REACHED before attempting the insert. If two requests race past the read, the trigger's atomic increment ensures the count remains correct, and the next request will fail the check.

Soft-delete semantics

Soft-delete (audit A.6 + B.6) sets deleted_at to a timestamp. The trigger detects this transition via OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL and decrements. Hard inserts of already-deleted rows are rare (test fixtures only) and don't increment.

Backfill

The migration backfills user_stats from existing data in the same transaction. Orphan audit (D.3 cascade FK) runs first to ensure no rows reference non-existent auth users.

Sanity check

After deployment, an operator query verifies the trigger stays consistent with ground truth:

SELECT u.user_id, u.solve_count, c.actual FROM user_stats u JOIN ( SELECT user_id, count(*) AS actual FROM solves WHERE deleted_at IS NULL GROUP BY user_id ) c ON c.user_id = u.user_id WHERE u.solve_count <> c.actual; -- Expected: zero rows
Resume Talking Point
"I replaced a count(*) cap check with an atomic per-user counter table maintained by trigger. The original had a TOCTOU race — two concurrent inserts could both pass the cap check and both insert, exceeding the limit. The counter table eliminates the race because the trigger runs inside the insert transaction with ON CONFLICT DO UPDATE atomic increment. The cap check is now a single index lookup instead of a full table scan; concurrent inserts cannot exceed the cap. The trigger also handles the soft-delete decrement so the counter stays consistent with reality."

Focus Trap on Modal Dialogs — Accessible Modals from Stdlib

frontend/src/hooks/useFocusTrap.ts · Audit I.7

The problem

Both SolveDetailModal and HotkeyHelp rendered role="dialog" but lacked aria-modal="true" and a focus trap. Without a trap, Tab moves focus into the page behind the modal. Without restoration, focus is lost when the modal closes. Keyboard and screen-reader users could not use the dialogs reliably.

Hand-rolled hook

The audit considered focus-trap-react. Hand-rolled was chosen to avoid the dependency for ~40 lines of code. The hook captures focusables on open, focuses the first, intercepts Tab/Shift+Tab to wrap, and restores focus on close.

const FOCUSABLE_SELECTOR = [ 'a[href]', 'button:not([disabled])', 'input:not([disabled])', 'select:not([disabled])', 'textarea:not([disabled])', '[tabindex]:not([tabindex="-1"])', ].join(','); const focusables = (root: HTMLElement): HTMLElement[] => Array.from(root.querySelectorAll<HTMLElement>(FOCUSABLE_SELECTOR)) .filter((el) => !el.hasAttribute('disabled')); export const useFocusTrap = (ref: RefObject<HTMLElement | null>, enabled = true) => { useEffect(() => { if (!enabled) return; const root = ref.current; if (!root) return; const previouslyFocused = document.activeElement as HTMLElement | null; focusables(root)[0]?.focus(); const handleKey = (e: KeyboardEvent) => { if (e.key !== 'Tab') return; const current = focusables(root); if (current.length === 0) { e.preventDefault(); return; } const first = current[0]!, last = current[current.length - 1]!; const active = document.activeElement; if (e.shiftKey && active === first) { e.preventDefault(); last.focus(); } else if (!e.shiftKey && active === last) { e.preventDefault(); first.focus(); } }; root.addEventListener('keydown', handleKey); return () => { root.removeEventListener('keydown', handleKey); previouslyFocused?.focus?.(); }; }, [ref, enabled]); };

Application

// SolveDetailModal.tsx <div ref={modalRef} role="dialog" aria-modal="true" aria-label="Solve details"> ... </div> const modalRef = useRef<HTMLDivElement>(null); useDismissOnOutsideClick(modalRef, onClose); // existing — Esc + click outside useFocusTrap(modalRef); // new in I.7

What it covers

  • Initial focus. First focusable in the modal is focused on mount.
  • Tab cycle. Tab from the last focusable wraps to the first; Shift+Tab from the first wraps to the last.
  • Focus restoration. On unmount, focus returns to whatever was focused before the modal opened.
  • aria-modal=true. Screen readers know to constrain virtual cursor to the dialog.

Tested via @testing-library + fireEvent. The five test cases (initial focus, Tab wrap, Shift+Tab wrap, restore on unmount, no-op when disabled) ship in useFocusTrap.test.tsx.

The boundary

React's componentDidCatch + getDerivedStateFromError are class-only. A thin class wrapper around a functional render is the standard pattern.

export class ErrorBoundary extends Component<Props, State> { state: State = { hasError: false, error: null }; static getDerivedStateFromError(error: Error): State { return { hasError: true, error }; } componentDidCatch(error: Error, errorInfo: ErrorInfo): void { // Log to console for now; vendor (Sentry / PostHog / etc.) deferred (H.6) console.error('ErrorBoundary caught:', error, errorInfo); toast.error('Something went wrong. Please reload.'); } handleReload = (): void => { window.location.reload(); }; render(): ReactNode { if (this.state.hasError) { return ( <div role="alert" className="error-boundary"> <h1>Something went wrong</h1> <p>The page couldn't load. Reload to try again.</p> <button onClick={this.handleReload}>Reload</button> </div> ); } return this.props.children; } }

SEC-1

Defense-in-Depth — Headers + RLS + Input Validation + Boot Checks

backend/app/__init__.py · Cluster B

Layered defense

No single mitigation is the line of defense. Each layer is a guess at what an attacker might bypass; the next layer assumes the previous one failed.

Boot-time config validation — B.4

create_app raises RuntimeError at boot if any of SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, or SHARE_SECRET is missing or SHARE_SECRET is shorter than 32 chars. Catches misconfiguration at deploy time, not on first request.

Security headers — B.7

Every response carries:

  • Content-Security-Policy-Report-Only (phase 1; flips to enforcing after burn-in per TODO_manual_edits.md)
  • X-Frame-Options: DENY (clickjacking prevention)
  • X-Content-Type-Options: nosniff (MIME-type sniffing prevention)
  • Referrer-Policy: no-referrer (do not leak URLs to third-party requests)
  • Strict-Transport-Security: max-age=31536000; includeSubDomains (HSTS)

JWT issuer check — B.1

jwt.decode is passed issuer=<SUPABASE_URL>/auth/v1 so a token minted by a different Supabase project (even if signature-valid) is rejected.

Tightened bare-except handling — B.2

The original except Exception in verify_token_local swallowed expired tokens, signature errors, and programmer bugs into one silent None. The audit split this into specific PyJWT exception classes; unexpected exceptions now propagate.

Per-route rate limits — B.10

Per-user (with IP fallback for anonymous routes). Documented in SD-5.

Per-route protection at runtime

Three layers: anon key → require_auth → RLS. A Bearer token from another project gets caught at the issuer check; one without a sub claim at the require_auth user check; one without a row to read at RLS. Each layer assumes the others might fail.

Production source maps off — B.9

vite.config.ts gates source maps on mode === 'development'. Production builds emit no *.map files. (Source maps reveal frontend logic for reverse-engineering.)

flask-cors version pin — B.8

Bumped past CVE range to flask-cors>=5.0.0,<6.

.env hygiene — B.14

.gitignore covers .env at any depth (.env, **/.env, *.env.local). Only public anon keys belong in VITE_* env vars on the frontend.
